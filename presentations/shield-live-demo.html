A verified, programmable surface inside TMM

Two jobs on a running TMM — no rebuild, no restart. Observe its internals live, and Enforce a safe verdict at a vulnerable function. Both authored from one tool: tmmtrace.

data plane PREVAIL-verified F5-signed

The gap

You can't see inside a running TMM — or act on it in place

  • Observe — iRules don't expose parser state, pool pressure, or which error branch a request took. A kernel uprobe that could costs ~1,000+ ns per hit — far too much for the poll loop.
  • Enforce — a CVE means fix in source → rebuild → re-qualify → redeploy. Weeks. The running fleet stays exposed the whole time, and nothing can act on a TMM that is already running.

What if a verified program could ride the poll loop — read what it needs, or return a safe value — armed in minutes, and prove what it did?

The tool

eBPF, in one slide

A small, sandboxed program that runs at a chosen point in a host's execution — a function's entry or exit, a network event, a tracepoint — each time that point is reached. Three properties matter here:

  • A verifier proves it safe — before it ever runs.
  • It attaches by naming the point, not patching code — the program carries an ELF section string (its SEC("…"), e.g. fentry/dtls_tx); the loader reads that name to know where and how to hook. No recompile of the thing it watches.
  • It's fast — compiled to native machine code (JIT), not interpreted.

Think iRules — but for TMM's internal C functions, and mathematically proven safe.

Why it's safe on the poll loop

The verifier is the whole point

Before a program loads, PREVAIL proves two things about it:

  • Memory safety — every read and write is bounds-checked; no wild pointers.
  • Bounded termination — a fixed instruction ceiling; it cannot loop forever.

The gate bites, in-cluster. PREVAIL runs in the toolbox pod on the pinned toolchain, so every probe is proven before it's signed — and a program that chases a raw pointer (reject_memory in our set) is REFUSED outright, not warned.

So a buggy — or hostile — program cannot crash or hang TMM. That is what earns it a place in the poll loop.

The mechanism

We put that VM inside TMM

  • One VM per TMM instance — core-pinned, on the data path, no shared-state lock.
  • Many programs at once — a fixed slot table (12), each an independent program at its own function, with its own mode and counters: observe here, enforce there, trace elsewhere — all live, all concurrent.
  • Arms at any function's entry pad — five reserved bytes the compiler leaves — while traffic flows.
  • Fully reversible — disarm restores the entry byte-for-byte, kernel-witnessed in process memory: TMM ends exactly as it started, no residue.
  • Splices nothing into TMM's logic — startup registers through INIT_FUNC; only the pad is touched.

The mechanism, one level down

What runs your program — the trampoline

  • Arm rewrites the 5-byte pad into a call to a per-slot trampoline stub. The pad is reserved dead space — so no real instruction is displaced or relocated.
  • On every entry the stub saves the argument registers and builds the ctx — a copy of the args, never live state — then calls the VM (JIT).
  • The program returns a verdict:
  • FALLTHROUGH → restore registers, continue into the untouched body. (Observe lives here — it reads, and steps aside.)
  • SAFE_RETURN → the safe value is placed in the CPU's return-value register (rax on x86-64), so the caller receives it as the function's result — the body never runs. (This is enforce.)

Per-slot, so arming one hook never disturbs another — and the register save is the measured ~8.8 ns the mechanism costs.

How we got here

Two compiles, one surface

Two clang runs, two artifacts: the substrate is compiled in once — off the data path; each program is compiled, proven, and signed before it loads.

The console — meet the tool

tmmtrace — one line of DSL, to a verified probe

tmmtrace is bpftrace, but for TMM's data plane. You write the intent as one line; it compiles to CO-RE bytecode, runs it through PREVAIL, F5-signs it, and arms it on a running pod — all from a toolbox pod you kubectl exec into, the way engineers already work.

grammar:  <fentry|fexit>/<hook> [/pred/] { count() | hist(x) | shield(v) }

observe:  fentry/http_parse_client_headers { count() }
enforce:  fentry/dtls_tx /args.sz > 16384/ { shield(2) }

pipeline: gen → clang → PREVAIL → F5-sign → arm(slot)

The same DSL authors all three: observe, cost, enforce.

Proven ceiling, measured floor

kubectl exec -it deploy/tmmtrace-toolbox -- \
  tmmtrace cost 'fentry/http_parse_client_headers { count() }'
  PROVEN CEILING (live, from THIS verified bytecode)
    11 insn · longest path ~22 cycles   (budget 800)
  MEASURED FLOOR (recorded microbenchmark)
    trampoline ~8.76 ns/call · + a small program ~13.8 ns total
  • Ceiling — budget_pass walks the verified bytecode's control-flow graph for its longest path → a worst-case cycle count. PREVAIL proves it halts; this bounds how long.
  • Floor — the trampoline's register save + dispatch, measured. A kernel uprobe is ~1,000+ ns — two orders of magnitude more.

Bounded above by proof, measured below by the mechanism — it cannot monopolize the poll loop.

Enforce, applied — the shield

Enforce's first job is a shield: return a safe value, skip the vulnerable body

A shield is enforce aimed at one bug — the same SAFE_RETURN mechanism, pointed at a vulnerable function. Target: dtls_tx, TMM's DTLS transmit path — a real, un-clamped fragment-length stack overflow live in this build (an internal finding; no CVE). The generated program:

// you write ONE line; tmmtrace generates this C:  fentry/dtls_tx /args.sz > 16384/ { shield(2) }
SEC("fentry/dtls_tx")   // SEC = ELF section; its NAME is the attach point (PREVAIL proves it, the loader arms dtls_tx entry)
__u64 tt_dtls_tx_shield(struct ls_ctx_generic *c) {   // c = the CTX: a snapshot the trampoline built
    __u64 sz = c->arg[3];                    // arg[3] = dtls_tx's 4th argument (the size), from a COPY — not live memory
    if (sz > 16384)                          // the exploit precondition (size past the on-stack buffer)
        return 1;   // MATCH → SAFE_RETURN: host puts ERR_BUF (2) in rax, body never runs
    return 0;  // FALLTHROUGH → the real dtls_tx runs, untouched
}

Reading it: c is the ctx — the snapshot the trampoline handed in: a copy of dtls_tx's argument registers, never live TMM memory, so the program can read the inputs but can't corrupt anything. arg[3] is the fragment size; over the buffer it returns 1 (SAFE_RETURN → the caller gets ERR_BUF and the crashing body is skipped), else 0 (the function runs normally).

Temporary, surgical, reversible — it retires when the patch lands. A bridge to the fix, armed in minutes rather than a release.

Enforce — authored in the same tool, armed deliberately

shield() — verified & signed for enforce, arming is gated

kubectl exec -it deploy/tmmtrace-toolbox -- \
  tmmtrace run 'fentry/dtls_tx /args.sz > 16384/ { shield(2) }'
  built (shield) verified=True
  signed prog sha256 : cb491dc30679...   mode-ceiling=enforce
  VERIFIED + SIGNED at mode-ceiling=enforce.   NOT armed — enforce is gated.

The tool authors and proves enforce; arming it on live traffic stays the one human step, because SAFE_RETURN skips a real function. Before arming, three properties are vetted:

  • The safe value is a return the caller already handles — dtls_tx returns ERR_BUF itself; the caller knows that path.
  • Skipping is a clean early-return — no half-updated state left behind.
  • The predicate reads a field available at entry — fentry runs before the body, so it sees inputs, not parsed results.

The evidence — run it, then read it

When enforce fires, it leaves proof

The dtls_tx shield from the last slide is signed for enforce but gated, and its overflow can't be triggered on this lab pod. So to exercise the evidence path end to end, we arm a monitor-mode stand-in that trips on ordinary traffic — it records the decision but lets the body run, so traffic is unaffected.

# 1. INSTRUMENT — arm a monitor probe; each SAFE_RETURN match emits an evidence record
kubectl exec -it deploy/tmmtrace-toolbox -- \
  tmmtrace arm 'fentry/http_parse_client_headers { count() }'
# 2. Window A — stream the evidence ring (already enabled: LS_TP_RING)
kubectl exec deploy/f5-tmm -c f5-tmm -- ls_drain --segment /dev/shm/ls_tp_ring --no-stats
# 3. Window B — drive traffic; each match pushes a record (first ~8, then sampled)
kubectl exec -it client -- sh -c 'curl -s http://11.11.11.99/'
{"ts_ns":…, "seq":2, "slot":1, "hook":"shield", "mode":"monitor", "gen":1, "verdict":1, "sz":0, "arg":[…]}
hookshield = an enforcement decision · verdict 1 = SAFE_RETURN
modemonitor = would-block (body still ran) · enforce = blocked
szsurfaced evidence field — for a dtls_tx shield, the oversized fragment size (here 0)

What this is — and isn't

Honest scope

  • Boots with nothing armed: no hardcoded shield — TMM comes up with the VM ready and nothing running. Its own boot log says so: no built-in shield armed — socket load is the only arming path. Every shield arrives signed, over the socket, into a running TMM.
  • Proven live: observe (count, fired 40/40), cost (ceiling + floor), and the mechanism — verified program, live arm, per-request verdict, pushed evidence in monitor.
  • Enforce is authored, verified, and signed at the enforce ceiling — but not yet armed on live traffic. That is the gated step, deliberately not taken until the three properties are vetted for a given hook.
  • SAFE_RETURN is the one decision outcome wired end-to-end — DROP / RESET / STEER / SAMPLE are authorable, but nothing host-side acts on them yet.
  • Captured bytes are a separate tool — tmmdump, by design; tmmtrace does summaries, not packet windows.
  • Per-instance, data plane only: arm every TMM to cover all traffic; control-plane CVE mitigation is a separate exercise, not addressed here.
