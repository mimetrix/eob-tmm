The problem

A CVE drops: “undisclosed traffic terminates TMM.”

  • Today's answer: fix in source → rebuild → re-qualify → redeploy. Weeks.
  • Meanwhile the running fleet stays exposed the entire time.
  • And nothing can act on a TMM that is already running, in place.

What if you could neutralize it on a live TMM in minutes — and prove it did?

The tool

eBPF, in one slide

A small, sandboxed program that runs at a chosen point in a host's execution — a function's entry or exit, a network event, a tracepoint — each time that point is reached. Three properties matter here:

  • A verifier proves it safe — before it ever runs.
  • It attaches without changing the host's code — no recompile of the thing it watches.
  • It's fast — compiled to native machine code (JIT), not interpreted.

Think iRules — but for TMM's internal C functions, and mathematically proven safe.

Why it's safe on the poll loop

The verifier is the whole point

Before a program loads, PREVAIL proves two things about it:

  • Memory safety — every read and write is bounds-checked; no wild pointers.
  • Bounded termination — a fixed instruction ceiling; it cannot loop forever.

So a buggy — or hostile — program cannot crash or hang TMM. That is what earns it a place in the poll loop.

The mechanism

We put that VM inside TMM

  • One VM per TMM instance — core-pinned, on the data path, no shared-state lock.
  • Many programs at once — a fixed slot table (12), each an independent program at its own function, with its own mode and counters: observe here, enforce there, trace elsewhere — all live, all concurrent.
  • Arms at any function's entry pad — five reserved bytes the compiler leaves — while traffic flows.
  • Fully reversible — disarm restores the entry byte-for-byte, kernel-witnessed in process memory: TMM ends exactly as it started, no residue.
  • Splices nothing into TMM's logic — startup registers through INIT_FUNC; only the pad is touched.

The capability

The Live Surface — one substrate, two missions

The same embedded VM and entry-pad machinery serves both — differing only in whether the host acts on the program's return value:

Observe

Read a running TMM's internal state at any function — parser state, pool pressure, error branches, per-request outcomes. Reaches what no iRule event exposes and no affordable kernel probe can.

Enforce

Act on the verdict — return a safe value, skip a vulnerable body. Same substrate, one extra step: the host applies the answer.

This lives in TMM's data plane — the proxy's poll loop, at connection and request scope — not the control plane. And shielding is only its first consumer.

The first consumer

A “shield” mitigates a CVE without patching

At the vulnerable function's entry, the program:

  • Reads the inputs — the fields that decide whether the exploit fires.
  • Recognizes the exploit condition — the same precondition a real fix would check.
  • Returns a safe value — skipping the crashing body. Fail closed, don't fall over.

Temporary, surgical, reversible — it retires when the patch lands. Not a replacement for the fix; a bridge to it, armed in minutes rather than a release.

The mechanism, one level down

What runs your program — the trampoline

  • Arm rewrites the 5-byte pad into a call to a per-slot trampoline stub. The pad is reserved dead space — so no real instruction is displaced or relocated.
  • On every entry the stub saves the argument registers and builds the ctx — a copy of the args, never live state — then calls the VM (JIT).
  • The program returns a verdict:
  • FALLTHROUGH → restore registers, continue into the untouched body.
  • SAFE_RETURN → the safe value goes in rax, and it returns straight to the caller — the body never runs.

Per-slot, so arming one hook never disturbs another — and the register save is the measured ~8.8 ns the mechanism costs.

The bytecode

What a real shield looks like — dtls_tx

Target: dtls_tx, TMM's DTLS transmit path — a real, un-clamped fragment-length stack overflow, live in this build (no CVE; an internal finding). The shield reads that precondition at entry:

/* arm at the entry of dtls_tx — the string IS the attach identity */
SEC("fentry/dtls_tx")
__u64 dtls_txguard(struct ls_ctx_generic *c) {
    struct ssl_ctx  *sc = (void*)c->arg[0];   // a COPY of the args
    __u64 sz = c->arg[3];
    bpf_probe_read(&cf,  ..., &sc->cf);          // bounds-checked read —
    bpf_probe_read(&mss, ..., &cf->mss);         // never a raw dereference

    if (mss > SSL_SZ_RDATA && sz > buffer_max)  // F5's OWN fix precondition
        return SAFE_RETURN;                    // skip the overflow, return ERR_BUF
    return FALLTHROUGH;
}
section = attach point probe_read = bounds-checked the check = the vendor's fix

The evidence

When it fires, it leaves proof

The counter

status → every hit on this instance. TMM's own tally. Answers “how many.”

The event stream

A pushed record — hook, mode, time, the context it saw — through a shared-memory ring, off the data path. Answers “show me the one it stopped.”

Rate-limited (first few, then sampled) so an attack flood can't turn your audit log into a self-inflicted DoS.

What this is — and isn't

Honest scope

  • Proven: the mechanism — verified program, live arm, per-request verdict, pushed evidence.
  • Today's demo is MONITOR: it recognizes and records; the body still ran (traffic was 200). Enforce would skip it.
  • The live-armed program is trivial — it trips unconditionally, to exercise the evidence path. The real dtls_tx shield is verified but blocked on one CO-RE relocator fix.
  • Per-instance: arm every TMM to cover all traffic; counters are per-instance, never a box-wide sum.
  • Data plane only: this lives in TMM's poll loop — the data path. Control-plane CVE mitigation (config daemons, management, BNK microservices) is a separate exercise, not addressed here.
