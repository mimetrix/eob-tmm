F5 TMM · BIG-IP Next for Kubernetes · as built

Five bytes change, and a running proxy starts explaining itself.

A verified eBPF program is loaded into a live TMM over a socket, patched into a function entry while traffic flows, and removed again leaving the bytes exactly as they were. No rebuild. No restart. This page is what exists and what it has been measured to do — not a proposal.

01 the mechanism

The compiler reserves five bytes at every function entry. That is the whole opening.

TMM is built with -fpatchable-function-entry=5,0, which costs 0.182% of binary size and leaves five nops after Intel CET's endbr64 guard. Arming overwrites exactly those five with a call to one shared trampoline. Nothing is displaced, so there is no instruction to relocate, no decoder in the process, and no window where another thread's program counter sits inside bytes being rewritten.

Arming is by symbol name, never by address. The name resolves through an index generated per build and gated on the binary's GNU build ID. That gate exists because rst_why occupied four different addresses across four builds of identical source — and because a stale address once armed the neighbouring function, which also carries a pad, so the patch succeeded, OK ARMED LIVE printed, and nothing fired across 16,000 requests. A pad cannot distinguish itself from another pad. A build ID can.

02 reach

Where it can go, counted from the binary rather than estimated.

71,296 symbols in TMM core, regenerated every build. The split is a property of how the binary is assembled — a flag applied to TMM's own compilation cannot reach two dozen separately-built components.

37,211 armable today
29,384 displaceable
4,701
37,211 armable now — padded, unique, endbr64 present, armed at entry+4.
29,384 need displacement — no pad at all. Reachable only by copying leading bytes verbatim, which is designed and unbuilt. OpenSSL's 1,781 linked symbols are in here.
4,701 padded but refused — no endbr64 (statics, .isra/.constprop clones). The arming path requires one today.

591 names in this build resolve to between 2 and 21 entries each. Arming refuses rather than picking one — most of the resolver's assertions are refusals, because a resolver that fell back to something plausible would reproduce the stale-address bug with extra steps.

03 the pipeline

Seven stages, each emitting an artifact the next one checks.

The identity that carries through all of it is the GNU build ID. Every index, every receipt and the arming gate key on the same string, so a mismatch anywhere is a refusal rather than a wrong answer.

1Compile the program clang -target bpf → .bpf.o with a fentry/<hook> section build
2Verify — in both directions PREVAIL must ACCEPT the shields and REJECT the known-bad ones build
3Sign what was verified Ed25519 over a 112-byte binding: program hash, hook, build range, ceiling, expiry build
4Index the packaged binary 71,296 hook entries + 63,796 signature entries — from the DEBs, because packaging relinks build
5Bake, and check the image against itself index build id == binary build id, and the compiled-in key == the key its programs carry build
6Load over the socket signature verified on a TMM thread, then admitted — or refused, and recorded live tmm
7Arm by name, watch, disarm five bytes; fired=17 under traffic; entry restored byte-identical live tmm

Stage 5's second check exists because its absence cost a full build-and-deploy cycle: an image was produced in which TMM trusted one key while the programs beside it were signed with another. Every other gate was green — build IDs matched, index matched binary — because none of them compared those two artifacts to each other.

04 the perimeter

What a signature settles, and what it leaves open.

An Ed25519 signature over the binding is checked inside TMM before a program is admitted. Unsigned, re-signed and altered programs are all refused — and the two tampering cases produce different messages, because they send an operator to different places.

The distinguishing message goes to the log, not the wire. The reply is a generic refusal so a forger cannot use it as an oracle for which half of a forgery to fix. Every operation also leaves one audit record: the op, the target, the program's hash, the serving binary's build ID, and the verdict the caller received quoted verbatim — attributed to the pid and uid the kernel reports, which the peer cannot forge.

And that is attribution, not authentication. The program is signed; the caller is anonymous. Anything that can reach the socket can ask. The verifying key is compiled into the binary with no revocation path, and a kubectl exec pid belongs to an API call TMM cannot see.

The trail is also not tamper-evident by format. A sequence number makes a deleted record visible as a gap and does nothing about a rewritten one; a hash chain would not help, since anything able to rewrite the log can recompute it. Durability rests on the sink — the container log stream, collected off-box.

06 what it is for

A proxy that can answer the one question it currently cannot.

TMM already knows why it tore a connection down — 14 macros over 4 functions, used at 1,090 call sites, each carrying a file, a line and a string in English. That vocabulary goes into a ring that overwrites, reaches no log, and is attached to no request. The client gets a bare TCP reset.

Armed at those sites, a program turns that into a record: tcp.c:3193 "ICMP unreachable received", flow_table.c:2618 "No local listener", and adjacent sites 993 and 994 firing together because a proxy is two connections. And because the program decides what is worth emitting — using a clock, in the poll loop — 120 host records became 4 program-emitted under 40 concurrent requests. That ratio, decided inside the data plane with nothing downstream counting, is the difference between telemetry and a decision.
