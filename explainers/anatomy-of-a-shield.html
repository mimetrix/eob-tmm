Anatomy of a shield — read ctx, return a verdict.

The companion deep-dive to the substrate explainer. A shield is a tiny function — this walks it end to end: what the hook hands it, the shield itself, the host that calls it, the compile → verify → load pipeline, and how the shape of ctx decides which CVEs are even shieldable. No prior eBPF needed.

Start here

The linked VM does nothing until you load bytecode

Linking libubpf.a is ordinary static linking — but on its own it does nothing. You've compiled in an empty engine: a VM with no program to run. It sits inert until a shield's bytecode is loaded into it at runtime — that's the decision, arriving as data, later, and passing a safety gate on the way in. Change the bytecode and you change what the box does, without touching the binary. (When it runs, the VM JIT-compiles the bytecode to native code — a JIT is a just-in-time compiler — so a shield invocation is a fast indirect call, not interpretation.)

So what do you load? A shield is a tiny function: it reads a context — ctx — and returns a verdict. Three pieces tell the whole story: the context it's handed, the shield itself, and the host that calls it.

The three pieces

A shield, end to end

First, what is ctx?

Short for context — the program's entire view of the world. At each hook (a designed-in point in TMM's code) the host packs the relevant facts into a small, typed struct (as you'll see: the frame's opcode, its length, a few header bytes) and hands the VM a pointer to it. The shield reads ctx, decides, and returns a number. It can't reach anything else — not other connections, not host memory, not the disk — only the fields this hook chose to expose. That narrowness is doing real work: it's half of why the verifier can prove the program safe (bounded reads over a known struct), and it's the context minimization the security model leans on — a probe sees only what its hook grants, and sensitive fields (TLS secrets, payloads) are withheld unless separately authorized. Different hook, different ctx.

1 · The context it's handed — ctx's actual type. The build's hook-point map defines it; the shield may read these fields and nothing else.
// ls_ctx — the typed context this hook exposes: five fields describing
// one frame. (A different hook — TLS, HTTP/2 — hands over a different ctx.)
struct ls_ctx {
    uint16_t opcode;       // the field the synthetic CVE abuses
    uint16_t payload_len;  // declared length from the frame header
    uint32_t avail_len;    // bytes actually buffered
    uint32_t mode;         // host-supplied: 1 = monitor, 2 = enforce
    uint8_t  head[16];     // first payload bytes, for richer predicates
};
2 · The shield itself — the whole thing: ls_shield.c, which compiles to the bytecode shield.bpf.o.
// ls_shield.c — a complete shield. Compiled with clang -target bpf,
// this ~6 lines becomes shield.bpf.o, the bytecode that runs at the hook.
// A shield is just a function: read ctx, return a verdict.
uint64_t ls_decision(struct ls_ctx *ctx)   // ctx = the frame's fields, above
{
    if (ctx->opcode >= 4)                  // the SIRT predicate: never a valid opcode
        return ctx->mode == ENFORCE ? 2    // 2 = matched → host DROPs
                                    : 1;   // 1 = matched, monitor → host passes
    return 0;                              // 0 = PASS — not the attack, forward it
}
3 · The host (TMM) that calls it — packs the frame into ctx, runs the shield, and acts on the return.
// at the designed-in hook point, once per frame — the host calls the VM
// like any function and acts on the return. No kernel. No injection.
struct ls_ctx ctx = { .opcode = op, .payload_len = len };  // pack the frame into ctx
uint64_t ret = 0;
ubpf_exec(g_vm, &ctx, sizeof(ctx), &ret);   // ← runs ls_decision() above, over ctx
// ret: 0 = PASS · 1 = matched/monitor (still passes) · 2 = matched → DROP
//      the host owns the outcomes; the shield only picks among them
Who defines ctx? TMM does — before any shield exists

Notice the ordering: the hook and its ctx are part of TMM's source, not the shield's. They're designed in ahead of time and emitted in the signed, per-build hook-point map; a shield is always written against a ctx that already exists — it consumes the contract, it never defines it. And that ctx is a designed window onto state TMM already holds at this point — the frame it's parsing, a connection's counters — a typed, curated slice, not raw memory. That's what separates this from injection (no guessing a struct's layout at some random function) and what lets a hook expose opcode while withholding the TLS secret sitting right beside it.

What you pay

A few extra nanoseconds per invocation — an indirect call into the JIT'd code instead of a straight C branch.

What you get

The decision leaves the build and becomes verified, swappable data you can load into a live, kernel-bypassing data plane — in hours, and provably unable to hang or corrupt it.

And it's smaller than it looks — no helpers, stock verifier

Look again at the shield: it calls nothing. It reads ctx and returns a number — the host does all the rest (counts hits, keeps the ring, applies the verdict). Two hard parts you'd expect simply aren't there. No helper functions: in eBPF, "helpers" are the calls a program makes back into the host — the surface you'd have to design, register, and lock down; a pure ctx→verdict program has none, so there's nothing to build or confine — it's sandboxed by construction. No verifier to extend: a bounded check over a typed struct is the textbook case the verifier already proves, so PREVAIL is used as-is — you describe the ctx layout, you don't modify the verifier. Anything stateful (a rate, a timestamp, a cross-flow counter) the host computes and drops into ctx. Helpers — letting the program touch host state directly — are an optional, later tier, not a prerequisite.

The hinge

How ctx decides which CVEs are shieldable

A shield can only stop what ctx lets it see. So the field the hook exposes and the condition the CVE makes dangerous are the same fact from two sides:

ctx.opcode — the field the hook exposes ⟷ opcode ≥ 4 — the condition the CVE abuses

the shield is just: if (ctx.opcode ≥ 4) drop() — it exists only because the field that reveals the exploit is in the context.

The shieldability rule

A CVE is shieldable at a hook only if that hook runs before the vulnerable operation and its ctx exposes the field(s) that tell the exploit apart. If no hook's ctx can express the condition, the CVE isn't runtime-shieldable — that's the residual dead zone, and it needs an engineering fix (an AI pipeline would flag it non-mitigable). The flip side is the opportunity: designing ctx richly and early is what makes whole future CVE classes catchable — which is why the hook-point map, not any single shield, is the real asset. One caveat — if the discriminating field is sensitive (say it only shows in decrypted payload), exposing it in ctx is also an authorization decision, so "is it shieldable?" and "may the probe see what it needs?" are the same question.

The one line

A shield is the smallest useful program: read a curated context, return one of a few host-owned verdicts. That's what makes it provably safe — and buildable with no helpers and a stock verifier.
