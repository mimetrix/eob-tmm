A design proposal · embedded userspace eBPF for F5 TMM

The behavior is identical. What changes is when you can change it.

TMM runs its own network stack and bypasses the Linux kernel — which makes it almost impossible to instrument from the outside. This is a plain-English case for what F5 could build: an eBPF virtual machine embedded inside TMM — and what that would buy over just compiling the logic in. One mechanism that could ride the same data plane across appliance, VE, and BIG-IP Next for Kubernetes.

Where this stands: a proposal, not a shipped feature. A working prototype proves the core mechanism outside TMM; embedding it in TMM is the opportunity this lays out.

The setup

Why TMM is a hard target

01 · Own stack

Its own network stack

TMM parses packets with its own TCP/IP code and connection tables — not the operating system's. The interesting logic lives in code the OS never touches.

02 · Kernel bypass

It bypasses the kernel

For speed, traffic goes NIC → TMM directly. The Linux kernel is simply not in the path, so kernel-level tools have nothing to observe.

03 · Sealed

Not easily instrumented

You can't safely bolt a probe onto a running, core-pinned poll loop from outside. Anything brittle here risks taking the data plane down.

The consequence

The usual tool for this — kernel eBPF — is structurally blind to TMM. It's not a permissions problem you fix by running as root; the traffic never passes through the place the kernel can watch.

A 30-second primer

What eBPF actually is

eBPF was the Linux kernel's answer to a hard question: how do you let people run custom code inside a live system without rebuilding it, and without risking a crash?

The move: you write a tiny program, and before it runs a verifier reads the whole thing and mathematically proves it will finish and only touches memory it's allowed to. Pass the proof and it runs at native speed at a chosen hook; fail and it never runs at all.

That pairing — change a live system + provably safe to do so — is the entire point. uBPF is just that engine packaged as a small library, minus the kernel — which is exactly what you need to put it somewhere the kernel can't reach.

The obvious objection

“eBPF already runs in the kernel — why not just use that?”

Because kernel eBPF and userspace eBPF are the same idea running in two different places — and where it runs decides what it can see. Kernel eBPF is the mature, default choice for almost everything. It just can't reach this particular target.

◇Kernel eBPF

Runs inside the OS kernel

✓Mature, ubiquitous, verified by the kernel's own verifier. The right tool for anything the kernel handles.
✓Sees syscalls, sockets, kernel network stack — the public highway all normal traffic drives on.
✕The packet path bypasses the kernel — so traffic-level observability has nothing to watch.
~It can reach TMM's own functions with uprobes — but every hit traps out of TMM into the kernel and back.
✕On a core-pinned poll loop that per-event boundary crossing is prohibitively costly — and it perturbs the very timing you're measuring.
Blind to the kernel-bypassed packet path; and where it can reach — code-level uprobes — the kernel round-trip per event defeats the purpose.
◆Userspace eBPF (uBPF)

The engine, embedded in the process itself

✓Same verified-program model — minus the kernel dependency. Just a small library you link in.
✓Would run inside TMM's own address space, at hooks on the private road — reaching state the kernel never sees.
✓Not an injection or a hack: F5 owns TMM's source, so the hook points would be designed in.
—You give up the kernel's built-in verifier, so you bring your own: PREVAIL, run before every load.
The only vantage point that reaches the data plane — because it lives in it.
“But couldn't you just use uprobes?”

Fair — kernel uprobes can attach to TMM's userspace functions, so this isn't pure blindness for code-level probing. The catch is cost: every hit traps from TMM into the kernel to run the program and back — a user↔kernel boundary crossing per event. On TMM's core-pinned, tight poll loop that's prohibitive, and it adds jitter to the exact timing you're trying to measure. An embedded uBPF probe has no boundary to cross — it's a direct in-process call at ~tens of ns. (A measured kernel-uprobe workload ran ~58% overhead versus ~12% for the equivalent userspace tool; the in-process call is cheaper still.) And for a shield the kernel can't even try — it forbids altering a function's outcome from a uprobe. Same signal, minus the kernel round-trip.

The rule of thumb

Use kernel eBPF wherever the kernel can see the target cheaply — it's the mature default, and F5 already ships it for kernel-mediated traffic. Reach for userspace eBPF for what the kernel can't reach without paying to cross the boundary: code on a kernel-bypass hot path, where a per-event kernel round-trip is the cost you can't pay. TMM is exactly that case.

What this is actually for

One box, two planes — and a CVE can land in either

The motivating use case would be Live Shield: a vendor-signed, auto-retiring mitigation that blocks a specific exploit path between maintenance windows — until the patched build ships on the normal schedule. But BIG-IP isn't one machine. It's two execution environments in one box, and each would need its own live-patch engine.

The punchline

It wouldn't be kernel or userspace eBPF — it would be both, under one signed catalog, each dispatched to the plane whose CVEs it can actually reach. The control plane would ride the mature kernel path; the data plane is the part only an embedded VM could protect — and the part nobody else can.

Across the whole portfolio

Same TMM, three very different homes

BIG-IP ships in three form factors, and the shield would ride all of them — because all three run the same TMM data plane. The mechanism would be identical everywhere. What varies is coverage: an in-TMM VM sees only what runs in TMM software, and how much that is depends on how much the platform offloads to hardware.

Why this matters

Notice the middle band never changes. A shield that lived in the host kernel would need a different story per form factor — and on a shared Kubernetes node you often can't control the kernel at all. Embedding the VM in TMM would sidestep that entirely: the data-plane shield would travel with TMM to bare metal, hypervisor, or container, unchanged. The more the ground shifts under BIG-IP, the more that portability is worth.

The honest boundary — hardware offload

An in-TMM VM sees only what runs in TMM software. On appliances, ePVA / FPGA / crypto offload deliberately keeps some traffic out of software — offloaded FastL4 flows switch in silicon — so that path is a genuine dead zone for the shield. But it's invisible to iRules and WASM just the same — the design already lists FastL4 as an iRule hole. It's a hardware boundary every software surface shares, not a cost unique to this approach. And the high-severity CVE classes here — L7 / parser bugs, bd/WAF termination — run in software anyway (a flow that needs inspection is escalated back into TMM), so they stay fully reachable. On VE, with no offload, the VM sees the entire data path.

The other half

Shields act. Tracepoints watch. Same machinery.

A shield is filter mode — the host acts on the program's return. Flip what the host does with that return, and the exact same hook becomes a tracepoint: record the value, never touch traffic. So the same investment would open a second, arguably bigger door — you could sprinkle designed-in, USDT-style tracepoints through TMM's source and hook them in-process with the VM: a whole observability surface kernel tracing structurally can't reach.

Why designed-in tracepoints, hooked in-process — and not just classic USDT?

◇Classic USDT

Static marker, hooked from outside

✓A named probe placed in the source — better than guessing symbol offsets. The right idea.
✕Hooked by an external tracer over a uprobe — kernel-mediated, so it's blind to TMM for the same reason everything else is.
✕Attaching means the injection path — the brittle mechanism this design already rejected.
Right marker, wrong consumer — the kernel can't watch a probe on the private road.
◆Tracepoints hooked in-process

Designed-in marker, hooked by the embedded VM

✓Named & typed by the developer at the exact spot that matters — a stable, versioned contract, relocated across builds, not a guessed offset.
✓Dark until lit — a tracepoint with nothing attached is essentially a nop; you pay only when a program is hooked.
✓On, then off — attach bytecode to capture one condition, flow, or tenant, then detach. bpftrace-for-TMM, no reboot, no TMOS rev.
✓Reaches in-TMM state — parser state machines, connection internals, inter-function latency, error-branch counts — none of which has an iRule field or a kernel vantage point.
Same "instrument by design" idea — but the consumer lives in the process, so it actually sees.
Why this compounds the value

The hard, expensive part — the embedded VM, the verifier, the hook-point map, the signing and lifecycle — would be built once. Shields (filter) and tracepoints (observe) would ride the same substrate. So every tracepoint added would be cheap new observability as bytecode, and the flight recorder, on-demand deep telemetry, and anomaly detection below would all fall out of the same machinery — reaching state that has no other surface at all.

It's never just one

Many open CVEs, many shields — loaded at once

A box in the wild rarely faces a single CVE. So the substrate wouldn't be one slot — it would hold a whole set of shields at once, each keyed to its own CVE, at its own hook, in its own mode, retiring on its own schedule. Independent lifecycle

Each retires on its own version

A shield would auto-disable the moment the running build crosses its fixed_in_version. Patch one CVE and only that shield retires — the rest keep protecting. A partially-upgraded HA group would retire per member.

Mixed modes & planes

Enforcing and soaking, side by side

A control-plane auth-bypass shield can enforce while a data-plane parser shield soaks in monitor — different modes, different planes, different engines, all in one registry.

Governed, not unlimited

A budget, because verified ≠ cheap

Each shield is a cheap call and an empty hook is one branch — but the engine still caps how many load and their total overhead. Protection is a budget line, tracked and signed-off, not a free-for-all.

Two shields, one hook

If two shields target the same hook point, the host runs them in a defined order and the first DROP wins — fail-safe by construction. Composing mitigations never produces a new control-flow effect; the host still owns every outcome.

The trade

Why accept a virtual machine at all?

Running bytecode through a VM costs a little more than a direct function call. You'd never pay that unless binding time mattered. For TMM, it's the whole game.

Speed

“Rebuild the host” means reship TMOS

Compiling the shield in makes it ride a quarterly release train with a maintenance window and a reboot. During an actively exploited CVE, that's not an option. Verified bytecode could ship in hours.

Blast radius

Verified & signed narrows who can push it

Compiled-in C has the full run of the process and rides TMM's entire QA cycle. Sandboxed, signed bytecode is provably bounded — so a faster, narrower path (SIRT signs a shield) could push it to a live box without a full code change's risk.

Under the hood

How the bytecode gets there

Linking libubpf.a is ordinary static linking — but on its own it does nothing. You've compiled in an empty engine: a VM with no program to run. It sits inert until a shield's bytecode is loaded into it at runtime — that's the decision, arriving as data, later, and passing a safety gate on the way in. Change the bytecode and you change what the box does, without touching the binary.

This is the shield — the whole thing. It's ls_shield.c → shield.bpf.o, the first two pipeline stages above.
// ls_shield.c — a complete Live Shield. Compiled with clang -target bpf,
// this ~6 lines becomes shield.bpf.o, the bytecode that flows through the
// pipeline above. A shield is just a function: read ctx, return a verdict.
uint64_t ls_decision(struct ls_ctx *ctx)   // ctx = the frame's fields
{
    if (ctx->opcode >= 4)                  // the SIRT predicate: never a valid opcode
        return ctx->mode == ENFORCE ? 2    // 2 = matched → host DROPs
                                    : 1;   // 1 = matched, monitor → host passes
    return 0;                              // 0 = PASS — not the attack, forward it
}
This is the host (TMM) — it calls the shield at the hook and acts on the return. The last two pipeline stages.
// at the designed-in hook point, once per frame — the host calls the VM
// like any function and acts on the return. No kernel. No injection.
struct ls_ctx ctx = { .opcode = op, .payload_len = len };  // pack the frame into ctx
uint64_t ret = 0;
ubpf_exec(g_vm, &ctx, sizeof(ctx), &ret);   // ← runs ls_decision() above, over ctx
// ret: 0 = PASS · 1 = matched/monitor (still passes) · 2 = matched → DROP
//      the host owns the outcomes; the shield only picks among them
What is ctx?

Short for context — the program's entire view of the world. At each hook the host packs the relevant facts into a small, typed struct (here: the frame's opcode, its length, a few header bytes) and hands the VM a pointer to it. The shield reads ctx, decides, and returns a number. It can't reach anything else — not other connections, not host memory, not the disk — only the fields this hook chose to expose. That narrowness is doing real work: it's half of why the verifier can prove the program safe (bounded reads over a known struct), and it's the context minimization the security model leans on — a probe sees only what its hook grants, and sensitive fields (TLS secrets, payloads) are withheld unless separately authorized. Different hook, different ctx: a TLS hook exposes handshake fields, an HTTP/2 hook exposes stream counts — always described by the build's typed hook-point map.

What you pay

A few extra nanoseconds per invocation — an indirect call into the JIT instead of a straight C branch.

What you get

The decision leaves the build and becomes verified, swappable data you can load into a live, kernel-bypassing data plane — in hours, provably unable to crash it.

Zoom out · the bigger picture

A third way to program the data plane

CVE shields would be just the first thing you do with it. TMM's real strength was never one feature — it's dynamic programmability: changing the data plane's behavior at runtime, no rebuild, no reboot. iRules established that. WASM extended it. Embedded eBPF could be the third surface — reaching a layer the other two can't, and the only one whose runtime changes would be provably safe.

The slot only eBPF fills

It's the one surface that is dynamically loadable and statically proven safe. That combination is what makes runtime change trustworthy on the paths where it's otherwise too dangerous to allow — the data-plane hot path and inline security controls. iRules stays the first-line traffic control; WASM owns expressive extensions; eBPF would own verified, near-zero-cost instrumentation and control. One spectrum, a clean division of labor — not a replacement.

Observability

bpftrace-for-TMM, on demand

Deep telemetry for one flow, tenant, or condition — loaded on, then off — reaching internal state no iRule field and no kernel probe can reach. New metrics as bytecode, no TMOS rev.

Diagnostics

A flight recorder

Keep a ring of recent internal state and freeze it when an error branch fires — the run-up into a failure, which a post-crash core dump no longer has. Ship a signed probe, then pull it.

Security

Beyond a single CVE

Protocol-anomaly detection at the parser, behavioral exploit detection on internal state, adaptive rate-limit / circuit-break driven by internal load — inline, verified, before any event fires.

Self-tuning

Read internal load, nudge a knob

Live hot-path profiling and admission control that react to TMM-internal health signals — poll-loop jitter, memory-pool pressure — that have no data-model surface at all.

The one line to remember

Linking the VM is ordinary. What would be radical is letting the rule stop being part of the build — and become verified data you can load into a live data plane the kernel can't even see.

That's the proposal. The mechanism is proven in a prototype; the opportunity is to bring it inside TMM.
