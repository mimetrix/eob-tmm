F5 · TMM · design proposal · one page

Give TMM its own verified eBPF engine.

Whoever shortens the distance from code commit to code deployed wins. TMM, BIG-IP's data-plane microkernel, already changes behaviour at runtime — config, profiles, WAF policy, iRules, an arriving WebAssembly tier — but each acts on the curated traffic model the proxy chose to expose. Reaching the code's own internals — a parser's error branch, the condition behind a crash — has one path: a build. So a new metric, a diagnostic probe and a mitigation for a live CVE all cost the same thing. A small userspace eBPF VM inside TMM changes the unit of change from a release to a signed artifact: it applies with no restart and no failover, and REVOKE disarms it by restoring the original bytes at a safe point. A static verifier is what makes that safe on the data path. CVE mitigation is the first use case because it is the most urgent, not the only one.

Why TMM is the right host — and why this isn't a general answer

◆ a proxy, not a forwarder

Three budgets, not one

Per request — microseconds; a hook is noise. Per packet in the proxy path (TCP reassembly, TLS records, L7 framing) — hundreds of nanoseconds; a hook is a few percent, affordable with measurement and sign-off. Pure FastL4 — accelerated L4 forwarding — tens of nanoseconds; not affordable, and we concede it. A forwarder has only the third. The pre-L7 CVEs live in the middle.

◆ vendor-owned, shipped, closed

The proof is required

F5 owns the source, so hooks are designed in and the build emits the hook map. F5 also can't ship a mitigation that might put the data plane into a repeatable crash-loop — which makes the verifier a precondition for the artifact existing, not a bolted-on feature.

The mechanism, end to end

author (a few lines of C) → clang -target bpf → PREVAIL verify (static memory-safety proof) → budget pass → sign the binding → load at a named hook → monitor → enforce → auto-retire

Two hook kinds cover the anticipated and the unanticipated: designed-in userland static-tracing (USDT) tracepoints with a curated, versioned context, and function-boundary probes at any function the build emitted as its own out-of-line body and listed in its signed hook map — the optimiser decides that set: an inlined function has no pad, so the hook lands on its nearest surviving caller, widening what a safe-return skips. Within that limit, a question nobody planned for needs no new build, once the enabling build ships. A program is a pure function of its context: it reads scalars, returns a verdict. The host owns every outcome (pass · drop · reset · safe-return · steer · sample) and applies whichever the hook allows; a program cannot invent control flow, inject a value, or reach memory it wasn't handed.

The security perimeter is the signature, not the verifier. Only F5-signed bytecode reaches the engine, and verification happens earlier — in F5's pipeline, never on anything an attacker supplied. So even a verifier bug is not remotely triggerable: exploiting it would also require compromising the hardware-held signing key. That moves the risk out of traffic-borne RCE — remote code execution triggered purely by sending traffic through the data path, needing no credentials or management-plane access — and into supply-chain/insider. The signature covers the whole binding — program hash, its one permitted hook, build range, mode ceiling, expiry — so a shield can't be replayed elsewhere or escalated to enforce.

What it unlocks

  • Deep observability — counters, latency across internal stages, a flight recorder that survives a TMM crash. bpftrace and tcpdump, for TMM.
  • Field diagnostics — ship a customer a signed probe, characterise the issue in situ, pull it. No debug build, often no waiting for a repro — and it complements core dumps rather than replacing them, since a probe only answers what someone already thought to ask.
  • Adaptive control — steer, sample, gate or shed on an internal signal, decided at the hook.
  • Runtime CVE mitigation — recognise a bug's precondition and take a safe outcome before the patched build is installed. It needs the same hooks, verifier and signing gate as everything above.

What it is not, stated plainly

Not a hot-patch — a shield stops a crash; it cannot reproduce the fix's corrected behaviour, so enforcing costs whatever the skipped work did. Not customer-facing programmability — the ABI (binary interface) is internal; F5 authors, F5 signs. Not free — the engine rides one enabling BIG-IP release. Not universal coverage — no bug-specific tracepoint has to be anticipated (the real advance), but a shieldable CVE still needs a surviving boundary before the fault that exposes the condition, offers a safe outcome, and fits its budget. The timing trap: an entry probe runs before the body, so a condition the body itself constructs is invisible to it. Coverage follows software: a fully accelerated flow hides its contents, though the offload decision is hookable TMM code — so declining the offload is itself a mitigation. What fraction of real advisories qualify is not known, and the retrospective study that would settle it needs no engineering. And the exposure gap is assumed, not observed — that an operator cannot always install a patched build at once. Not measured yet — nobody has the always-on cost of compiling TMM with patchable function entries, and that number decides everything.

Nothing here has to be committed to in order to evaluate it. Two things settle on paper with no engineering at all — the retrospective study above, and which way the fuel trade-off goes. Then three decide whether the rest is worth designing: (1) measure the compiler flag twice — its idle cost with nothing armed, then its armed cost at rate; (2) settle a context model that verifies against real TMM debug info; (3) arm one hook end-to-end in a lab TMM with core dumps still readable. Land all three and what follows is a programme — subsystem-scale, not a feature; if any fails, the idea dies early and cheaply.

A design proposal, not a commitment to implement. Design docs, a self-review register and self-checking ABI artifacts accompany it: start with the reading map.
