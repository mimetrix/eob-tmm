F5 TMM· Embedded verified eBPF· design proposal

Let the running data plane change at machine speed — safely, without a release.

The AI age collapsed every delivery timeline. New capability, new telemetry, and urgent fixes are all expected in hours now — not on the next quarterly build. Everywhere else, when something needs to change, it changes today. Call it the race to zero. Inside TMM, that same change is still measured in releases.

And the timing cuts F5's way. Generative AI has nothing to say about line-rate processing — the data plane is the one layer it can't disrupt — and the proxy sits on a unique, monetizable data source no model or endpoint sees.

One requirement, two faces — co-equal

program Extend what it does

New telemetry, new logic, new behavior in the running data plane — delivered as verified bytecode against designed-in hook points, no rebuild.

protect Mitigate what's live

Block a specific threat in place, in hours, with no release — a surgical, reversible control that stands in until the patched build ships on schedule.

The same act, either way: change the running data plane's behavior — safely, now.

Why it's hard here. TMM is a kernel-bypass microkernel — its own network stack, core-pinned poll loops. That design is why it's fast, and why it's rigid: the industry's answer to safe runtime change, kernel eBPF, is structurally blind to TMM because TMM bypassed the kernel. Changing it today means patch C → rebuild → re-qualify → ride the release train.

The proposal: embed a small, verified eBPF VM inside TMM at designed-in hook points. Behavior loads as bytecode — statically proven bounded and terminating before it runs. No rebuild, no reboot. Dynamically loadable and provably safe — the one surface that is both.

What one surface unlocks

  • Live mitigation — a signed, auto-retiring shield for a CVE nothing else can reach in TMM.
  • New telemetry & logic — metrics and behavior shipped as bytecode, no TMOS rev.
  • Black-box observability — see inside a kernel-bypassed data plane (tmmtrace · tmmdump).
  • AI-authored, still safe — the verifier is a fail-closed gate; blast radius bounded by proof, not trust.

■ why it's safe to run inline

Stock PREVAIL verifier, no custom helpers, host-owned outcomes, signed hook-point map. A program can only read a curated ctx and return a code that picks one outcome the host already owns — PASS / DROP / RESET. It cannot hang, scribble memory, or invent control flow.

The data plane should stop being the holdout.

A verified, in-process programmability surface is how the fastest layer in the stack catches up to a machine-speed world — one surface serving observability, live mitigation, and even machine-speed authorship, each change proven safe before it runs. Champion the direction.
