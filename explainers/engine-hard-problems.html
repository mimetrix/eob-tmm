F5 TMM · engineering register · the honest half

Before we build it: where this gets hard.

The proposal says a verified eBPF engine is safe to run inside TMM. True — as far as it goes. This page is the other half: the load-bearing problems a security review will raise first, stated plainly, before anyone has to ask.

None of them is a show-stopper. Each has a known mitigation and a clear day-one path. They are the work to do — not a verdict against doing it.

01 time

A proof that a program terminates is not a promise it fits the budget.

The verifier proves every program halts — it bounds loop iterations, so nothing runs forever. That is not a worst-case execution time (WCET): the longest it can actually take on the hardware. Halting says nothing about fitting TMM's per-packet budget.

the claim to retire

“It's verified as bounded, so it can't hang the poll loop.”

And the resource is unforgiving. TMM's poll loop is single-threaded, un-preemptible, run-to-completion — there is no OS underneath to preempt an overrunning hook. Every hook borrows cycles from the same loop, so one misjudged hook starves every flow on that core. Poll loops are managed carefully or not at all.

day one

  • A per-hook instruction-budget ceiling, enforced at load — reject bytecode over budget.
  • A runtime deadline / watchdog that short-circuits or unloads a hook that overruns.
  • Budget by path class — hot (per-packet) hooks tight; cold / error-path hooks looser.

Note: the verifier is necessary, not sufficient, for hot-path safety.

02 the interface

The VM is the easy 10%. The interface is the other 90%.

What a program sees — the ctx: which fields of the flow, the buffer, the profile — plus the verified helper surface and the map model: that is the real design. And it is a permanent, versioned ABI you carry the moment you ship it.

the claim to retire

“The base tier is a trivial pure function of ctx.” The base ctx is real, forever-facing interface work.

The good news, stated precisely: this work is exactly the input the verifier is built to consume. The task is “write the program-type descriptor” — the ctx layout, memory regions, helper prototypes — not “modify the verifier.” The no-verifier-fork claim survives; the effort estimate does not.

day one

  • Ship a minimal, read-only ctx per hook + its program-type descriptor.

Deferred: helpers. Each one is a new ABI to secure and a new verifier prototype — ctx-first, helpers-later.

03 shared state

TMM is not one kernel. It's N core-pinned kernels with their own state fabric.

Multiple TMM instances per box (CMP), plus connection mirroring to an HA peer, make map and state semantics harder than Linux's single-kernel case — not easier.

the claim to retire

“Maps work like they do in Linux.”

day one

  • Per-CPU maps only — no cross-TMM sharing. Matches the core-pinned model; no locking.
  • State that must survive failover rides TMM's existing mirroring channel — don't reinvent HA replication inside the map layer.

Deferred: shared, writable maps across TMMs — they need an explicit concurrency and reconciliation model.

04 the trust surface

The verifier and its JIT run inside the crown-jewel process. This is the one a review presses hardest.

The engine JITs native code into TMM's own address space. An unsound verifier, or a buggy JIT, is arbitrary execution in the data plane — the single biggest risk class eBPF carries, relocated into TMM. It is sharper now that the source has been exposed: an adversary with the code can hunt soundness bugs directly.

the load-bearing point

The perimeter is the signing gate, not the verifier. Only F5-signed bytecode ever reaches the verifier or JIT — attacker-controlled input never touches them. So a soundness bug is not a traffic-borne RCE; it's a supply-chain concern, gated by signing-key protection.

attacker-controlled bytecode → signing gate✗ rejected
F5-signed bytecode → verify → JIT✓ runs

And verified ≠ correct. The proof is about memory-safety and termination, not intent — a verified, signed program can still black-hole traffic. So blast radius needs its own bound, separate from the proof.

day one

  • Signing gate + HSM-backed key protection — the real perimeter; protect it accordingly.
  • JIT hardening (W^X, guard pages) and an interpreter-only high-assurance build option — trade JIT speed for a smaller native-code surface where it matters most.
  • A control-plane canary that auto-unloads on a health signal — the proof bounds crashes; the canary bounds a bad-but-valid program.

06 the review

The verifier is the floor, not the building.

It gives you memory-safety and termination — not WCET, not correctness, and not immunity from its own bugs. The engine is defensible because the signing gate keeps attacker input away from the verifier and JIT, a budget + watchdog bounds execution time, and a canary bounds the blast radius of a valid-but-bad program. Verification is one layer of several.

This design is not self-certifying. Everything here is the engineering input to a formal Threat Model Analysis (TMA) by F5 security — a gating prerequisite before implementation, not a formality. The trust surface (§04) in particular must be threat-modeled and signed off. This register is what to bring to that review, not a substitute for it.
