F5 TMM · engineering register · the honest half

Building it: where this gets hard.

The proposal says a verified eBPF engine is safe to run inside TMM — F5's data-plane microkernel, with its own scheduler and stacks, bypassing the Linux kernel for all traffic. True, as far as it goes. This page is the other half: the problems it raises — engineering as much as security.

None is a show-stopper: each has a known mitigation and a day-one path. The work to do, not a verdict against doing it.

Accuracy note — updated 2026-08-20. This page was written as a proposal. The data-plane mechanism described here now runs on a live TMM: a shield is loaded over a socket into an already-running process, armed at a function entry while traffic flows, and disarmed — no rebuild, no restart. Where the page still reads “would”, treat the mechanism as built and the outcome as not yet shown.

Built since this page was written. Signature verification is no longer part of the proposal — an Ed25519 signature over the program's binding is checked inside TMM before admission, and unsigned, re-signed and altered programs are refused. The hook index is generated per build, so a hook is named rather than addressed, and arming is refused when the index and the running binary disagree.

Updated 2026-09-03 — a named CVE HAS now been mitigated on live traffic (CVE-2025-41414: crashed by one client request, prevented by a selective shield, 10/10 on the known-positive with 0/10 false positives). The sentence that follows is kept as the record of what was true when this page was written. No CVE had been mitigated on live traffic Demonstrated 2026-08-24, with the condition synthesised: given the vulnerable input, an armed shield in enforce mode returns SAFE_RETURN and TMM survives; in monitor mode it falls through and the same binary dies on the dereference. Real signed program, real VM, real TMM process, real dereference — but the condition is built directly rather than reached by traffic, because no CRD can create it. So the mechanism is shown to prevent the crash; no reachable attack path has been closed. Both claims, and the boundary between them, are set out in cve-selftest.md. — the mechanism is shown, the outcome is not. The per-call cost of an armed hook on the data path is unmeasured. A floor exists: a small program executes in ≤ 11 ns on the compiled path, and that figure is bounded by the timer measuring it rather than by the program, so it excludes the trampoline's register save and restore, the call and return, and cache effects under real traffic. Quote the floor as a floor and nothing as a per-packet cost.

And the perimeter moved rather than closed. The loader authenticates the program, not the caller: anything able to reach its socket may ask, the verifying key is compiled into the binary with no revocation path. Every operation is recorded as of 2026-08-20 — one line each, carrying the op, its target, the program's hash, the build ID of the binary that served it, and the verdict the caller received verbatim — and the asker is the pid and uid the kernel reports for the connecting process, which cannot be forged and is still a process rather than a person. That gap — an identity, not a record — is what still makes this lab-only.

01 time

A proof that a program terminates is not a promise it fits the budget.

The verifier proves every program halts — it bounds loop iterations. (With --termination enabled — not the default of PREVAIL, the abstract-interpretation eBPF verifier this design uses.) That is not a worst-case execution time (WCET): the longest it can actually take on the hardware. Halting says nothing about fitting the budget at the hook it runs on.

the claim to retire

“It's verified as bounded, so it can't hang the poll loop.”

TMM's poll loop is single-threaded, un-preemptible, run-to-completion — no OS underneath to preempt an overrunning hook, and every hook borrows cycles from the same loop, so one misjudged hook starves every flow on that core.

The fix is two layers — and only one is free.

① at admission · static · once, off-box

The budget pass

Cost the worst-case path through the program's CFG — finite, because loops are proven-bounded — against the hook's budget, per invocation, gated by its rate class (path_class, the table below). That class reads as structure ∧ adversarial reachability: anything an attacker can drive at will is hot wherever it sits in the source. Over budget → reject, fail closed.

runtime cost: none · a build artifact

② at runtime · every execution

The runtime guard

Instruction count is not time — warm cache versus cold changes everything — so something must stop a slow execution as it runs. Irreducible, with a small per-execution cost; which mechanism is the open question below. Note what “terminating” buys alone: PREVAIL's ceiling is 100,000 loop iterations, ~300 µs at ~10 instructions each on a 3 GHz core — so a proven-terminating program can stall the loop for a third of a millisecond. That is the argument for ①.

runtime cost: small, bounded · live machinery

the trilemma — the hardest open question here

Enforcing a time bound with no preemption leaves three mechanisms, each costing something we have claimed. Fuel (a counter at loop back-edges) is cheap and deterministic — but uBPF states its limit “has no effect on JIT'd programs”, so fuel means patching uBPF's JIT. (The limit does work in uBPF's interpreter, so an interpreter-only high-assurance build has enforceable fuel with no fork.) Wall-clock reads a clock at back-edges — but on aarch64 that counter ticks at 10–40 ns granularity against a hot-hook budget of tens of nanoseconds, so it is not measurable at the granularity that matters on half our platforms. Signals and timers cost a syscall per invocation — a non-starter.

So fuel is the mechanism, not the optional extra, and the wall-clock deadline is reporting rather than enforcement. Decide in the room which of the three we give up: the run-to-completion loop, the unmodified uBPF, or enforce mode on hot hooks. The good answer is to fork uBPF's JIT for back-edge fuel, own it, and upstream it.

what is plausible per packet — ranked, all conditional on measurement nobody has taken

Observability with a sampling divisor: high confidence — cost is adjustable downward by construction. Enforcement on an exceptional branch, time-boxed: good, and where the flagship CVE classes sit — conditional on the fuel guard, since an unbudgeted program on an attacker-driven branch is the worst case. Enforcement on the common path at line rate: doubtful without a burst-capable invocation form (§05). The contents of an offloaded flow: no — they never enter TMM software.

Both levers are narrower than they look: a sampling divisor is useless for enforcement (you cannot block one in N instances of an exploit), and time-boxing applies only to mitigation — a few percent for an exposure window is a different trade from a few percent permanently, and does not transfer to always-on telemetry.

“verified, JIT” names a configuration, not a property

Both defaults have to be stated to be a claim, and neither is the safe one. PREVAIL ignores termination unless asked, runs without strict mode, and permits division by zero; uBPF ships with constant blinding and the undefined-behaviour check off. Every one of those was read out of config.hpp and ubpf.h, not assumed. The full stage-by-stage pipeline — what drives each stage and the artifact it emits — is in engine-hard-problems.md; only run executes per packet, and everything before it is amortized once per build or once per program.

the problem is also the pitch

Setting those budgets is itself an observability problem — exactly what a few designed-in USDTs (userland statically-defined tracing — probe points built into the source) expose: poll-loop duration per iteration, per-hook execution cost, a stall tripwire. The engine instruments the very loop it runs in.

02 the interface

The VM is the easy 10%. The interface is the other 90%.

What a program sees — the ctx: which fields of the flow, the buffer, the profile — plus the verified helper surface and the map model. That is the real design, and a permanent, versioned ABI once shipped.

the claim to retire

“The base tier is a trivial pure function of ctx.”

The good news, stated precisely: the task is “write the program-type descriptor” — ctx layout, memory regions, helper prototypes — not “modify the verifier.” The no-verifier-fork claim survives; the effort estimate does not.

the interface is the USDT catalog

The designed-in half of that interface is a catalog of well-defined USDTs — one per hook, each a curated ctx — and the other half the per-build typed-argument map that function-boundary probes read. Together they are the ceiling on what the engine can observe or enforce: the catalog bounds the anticipated surface; boundary probes reach any function that survived the build as its own out-of-line body and whose arguments expose the fault. Getting both right is not incidental to the project — it is the project, and the permanent ABI.

day one

  • Ship a minimal ctx per hook + its program-type descriptor — built as a per-core scratch copy, discarded on fall-through, never a live view of TMM state. PREVAIL's descriptor expresses no read-only region, so a verified program can write every byte of its ctx: handed the live argument frame, an observe-only program would be an argument-injection primitive. The copy is the cost, and the copy is what to measure.
  • Start from what's already there — no blank page. TMM's code already holds the state these USDTs expose: the connection table, the TLS record layer, the L7 parser state, the bd/plugin internals, the poll-loop counters. So the first USDTs are a curated window onto structures that already exist, and can begin the day the engine lands.

Deferred: helpers. Each one is a new ABI to secure and a new verifier prototype — ctx-first, helpers-later.

03 shared state

TMM is not one kernel. It's N core-pinned kernels with their own state fabric.

Multiple TMM instances per box (CMP — clustered multiprocessing, one TMM pinned per core), plus connection mirroring to an HA peer, make map and state semantics harder than Linux's single-kernel case, not easier.

the claim to retire

“Maps work like they do in Linux.”

day one

  • When the helper tier lands (deferred): per-CPU maps only — no cross-TMM sharing. The base tier registers no helpers, so it has no map access.
  • State that must survive failover rides TMM's existing mirroring channel — don't reinvent HA replication in the map layer.

Deferred: shared, writable maps across TMMs — they need an explicit concurrency and reconciliation model.

04 the trust surface

The JIT emits native code into the crown-jewel process, and the verifier decides what reaches it.

PREVAIL runs outside TMM — in F5's build/admission pipeline, never in TMM's address space and never on attacker-supplied input — yet an unsound verifier or a buggy JIT still means arbitrary native code in the data plane: the biggest risk class eBPF carries, relocated into TMM.†

the point

The perimeter is the signing gate, not the verifier. Only F5-signed bytecode ever reaches the verifier or JIT — attacker-controlled input never touches them. So a soundness bug is not a traffic-borne RCE — remote code execution triggered purely by sending traffic through the data path, needing no credentials and no management-plane access; it's a supply-chain concern gated by signing-key protection.

attacker-controlled bytecode → signing gate✗ rejected
F5-signed bytecode → verify → JIT✓ runs

And verified ≠ correct. The proof covers memory-safety and termination, not intent — a verified, signed program can still black-hole traffic, so blast radius needs its own bound.

day one

  • Signing gate + HSM-backed key protection — a hardware security module holding the signing key. This is the real perimeter; protect it accordingly.
  • JIT hardening (W^X, guard pages) and an interpreter-only high-assurance build option — trade JIT speed for a smaller native-code surface.
  • A control-plane canary that auto-unloads on a health signal — the proof bounds crashes, the canary a bad-but-valid program.
we're not alone on this

“How do you know the verifier is sound?” has no satisfying answer of the form it's widely used. What works is inspectability — tooling that steps through the abstract interpretation so a reviewer can see why a program was accepted, and so the verifier can be unit-tested against adversarial input. That is the form soundness evidence has to take for a TMA (Threat Model Analysis — F5's formal security review, gating here). Establish early whether PREVAIL offers it: the signing gate bounds who could exploit a soundness bug, but only auditability reduces the chance there is one.

† Sharper still given source-code exposure — an adversary holding the code can hunt soundness bugs directly. Which is the point: secrecy was never the defense; the signing gate is. The perimeter holds whether or not the source is public.

05 further concerns

Thirteen more to get ahead of — and one of them is the biggest item here.

The four above are the ones the design turns on; these are the next tier. Read the list with its severity in mind — thirteen equal-looking boxes overstate the risk. Exactly one is both unavoidable and hard: the safe point. Two are not open questions at all, four are ordinary lifecycle and governance work, and four exist only because function-boundary probes are the mechanism. An earlier draft offered an escape from those four — fall back to designed-in call sites and live-text patching goes away — but that fallback was removed on 2026-08-13, its reach being fixed at build time, which is precisely what a CVE defeats. These four are now unconditional.

item zero · the safe point — which is three items

Every in-TMM piece once assumed “a safe point between poll-loop iterations that picks up a load request.” Nothing needs picking up: parse, verify and JIT run on a control thread, and what reaches the hot path is one ordered store. The poll loop is the cheapest source of the rendezvous and of quiescence, not the only one. Exactly one capability has no substitute: an atomic multi-slot change — forfeited rather than blocking, since day one is one program per hook.

certification · FIPS / Common Criteria

An appliance validated under FIPS 140-2/3 or Common Criteria that also loads data-plane code at runtime is a certification problem. Evaluators may not accept “it's signed,” which can force a dynamic-load-disabled certified mode. Likely the biggest productization gate.

keep the verifier out of TMM

PREVAIL (heavy C++/Boost) verifies at build and control-plane time; only the small runtime and a signature check live in TMM. This shrinks the §04 surface.

boundary-probe ctx is build-specific

A function-boundary probe's contract — function X's typed arguments at build Y — is regenerated every build: more reach than a versioned USDT ctx, looser contract. The signed hook map and the binding's build range keep it honest.

uBPF JIT maturity

§04 is really “the verifier and this JIT.” uBPF's JIT is far less battle-tested than the kernel's — audit, harden or fork it, or default to the interpreter.

the optimiser decides the hookable set

The flag pads the entries the build emits, and at -O2 that is a subset of the source: inlining removes an entry (pushing the boundary out to the caller — a wider skip radius, not lost reach), -fipa-icf folds identical bodies so arming one arms the other, and clones change both symbol and argument list. Publish the set as a build artifact and treat it as the contract.

invocation granularity · per-packet vs. batched

eBPF's calling convention takes one ctx, once — it cannot express “here is a vector of 256 packets.” TMM is the favorable case: a proxy, per-flow rather than per-vector. What remains is per-invocation overhead where TMM does batch, which wants a burst-capable invocation form — §01's enabling mechanism for common-path enforcement.

handlers running at the same time

Within one instance there is no concurrency at all — single-threaded, un-preemptible, run-to-completion — which is why per-core counters need no atomics and a per-core depth guard answers re-entrancy completely. Across instances there is full N-way parallelism, so shared state is a real concurrency problem. The one real seam: the loader mutating a slot while that slot's program runs on another core.

many programs armed at once

Different hooks at once, yes; two chained on one hook, refused. Every argument here is written for one program at one hook, and arming two raises four things: a second load must be distinctly rejected, never silently overwritten; chaining needs a total order over the outcome set, not plumbing; nothing bounds cumulative armed cost, since a flow pays the sum of the hooks it traverses; and worst, a shield that safe-returns past a body containing another hook silences it, so a masked hook must report masked, never zero.

multi-tenancy · partitions · vCMP

BIG-IP is deeply multi-tenant, and vCMP guests each run their own TMM. A program's scope, authorization and blast radius must be tenant-aware from day one.

ISSU + failover

ISSU (in-service software upgrade) and HA failover need defined behaviour: loaded programs re-verify and reload on the new TMM, with explicit map-state handling. (Extends §03.)

post-mortem debuggability — it cuts both ways

The first concern support engineers raise. A backtrace through a hooked function is garbage without correct CFI on the trampoline, and a PC inside JIT'd code has no symbol unless the loader registers the region. The one rarely listed: a core dump must record which shields were armed — without that, every future crash on a box that has ever loaded one is ambiguous, a cost paid even on crashes no shield touched.

jitter-sensitive deployments

Trading, 5G UPF and similar won't tolerate any added per-packet jitter — expect a per-hook or per-deployment opt-out.

07 the reality

and the honest size of it

An earlier draft called this “hundreds of lines, not subsystems.” Reviewed against what each item requires, a defensible v1 on two CPU architectures is subsystem-scale work, not a feature, plus the TMA and certification engagement. No month or headcount figure is offered: a proposal, not a plan. The items that grew most are the safe point, arm/disarm, and the hook-map generator — a parameter classifier over DWARF against an optimised build, the least-proven engineering assumption here.

The reframe that matters: the subsystem being added is not the VM. It is a code-patching, live-text, dynamic-code-loading facility inside the crown-jewel process, with its own build-pipeline toolchain and a permanent per-build ABI. Describing that as smaller than it is doesn't make it easier to say yes to; it makes the yes collapse in month nine. So this register argues for a sequencing, not a commitment. Of the three questions that decide whether the rest is worth designing, one is now half-answered — arming one hook end-to-end in a live TMM is done, though whether core dumps stay readable through a patched entry was never tested. The other two are open: measure the compiler flag twice — idle, then armed at rate, which remains unmeasured — and settle a ctx model that verifies against real TMM debug info.

The verifier is the floor, not the building.

It gives you memory-safety and termination — not WCET, not correctness, not immunity from its own bugs. The engine is defensible because the signing gate keeps attacker input away from the verifier and JIT, a budget + fuel guard bounds execution time, and a canary bounds a valid-but-bad program. Verification is one layer of several.

This design is not self-certifying. Everything here is engineering input to a formal TMA by F5 security — a gating prerequisite before implementation, not a formality. The trust surface (§04) in particular must be threat-modeled and signed off. This register is what to bring to that review, not a substitute for it.
