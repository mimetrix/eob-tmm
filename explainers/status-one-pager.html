Extending a shipped data plane in place, after it has deployed

TMM is already programmable — iRules run in it live. But an iRule can only act on the objects F5 exposed, at the events F5 placed, both fixed when the binary shipped. This loads verified bytecode at any function entry of a running TMM — no rebuild, no restart, no dropped traffic — so the data plane can be given new observability and new per-flow logic that no shipped event reaches, and the set of things it can do stops being frozen at ship time. Static verification is what makes that surface safe to hand to the field. The mechanism is proven on a live cluster; the applications are at different stages, and this page keeps them apart.

Each is a capability, tiered by how far it is actually carried. measured live shown on synthetic input not yet shown

  • Surface answers TMM computes and discards.measured live
    TMM decides, per flow, things its object model never exposes — why a connection was reset, which parse rule tripped. No iRule command or event returns them. A program at the right entry turns any of them into a signal, with no release. rst_why → tcp.c:4689 "TCP RST from remote system", per flow, off live traffic
  • Make a decision inside the poll loop, not report from outside it.measured live
    A program that keys on an internal value and a clock, and emits only when its own threshold is crossed — logic with no iRule event to hang from. rate gate: host records vs program-emitted, decided in the data path
  • Change what an internal function returns.shown on synthetic input
    Not reject-at-an-event — return a chosen value from an arbitrary internal function, which the host acts on. This is the step from telemetry to control. enforce → SAFE_RETURN, survived · monitor → FALLTHROUGH, fatal · one variable
  • Add the capability after deployment.measured live
    Arm a new attach point on a running process and remove it again, leaving the bytes as they were. What the data plane can be asked to do changes in seconds. ARMED LIVE entry=0xcd1004 (no restart) · fires 1:1, 40 req → +40 · DISARMED LIVE

The novel column is arbitrary internal reach + can enforce + verified + runtime-added. Nothing else has all four. A uprobe is the closest, and it can neither change an outcome nor be handed to the field safely.

Proven mechanism, on a live TMM
  • Loaded into a running process, checked inside TMM signature=verified
  • No hand-written layout numbers — derived from the build, two DWARF readers must agree, refuses on build-id mismatch 13 values, readelf ≡ gdb
  • Every op recorded with a kernel-attested asker SO_PEERCRED · 47 assertions
  • Reproducible from nothing — both machines rebuilt, suites green
The honest boundaries — so the claim survives review
  • The number the case rests on is unmeasured. Per-call cost on the data path. A low figure is what separates this from a uprobe; it is now measurable and is the next task.
  • Enforcement is shown on a synthesised input. The crash/survive flip used a condition that cannot occur by configuration — the guard sits one frame up.
  • CVE mitigation on BNK is off the table — not a weakness of the mechanism. Of the tracked CVEs, essentially none are inside TMM; they are dependency CVEs in other containers. And a shield does not move a scanner.
  • Those CVE counts are uncited and marked NOT_RETRIEVED until re-run and cached.
  • Placement is entry-only today — a check on a value the function computes needs displacement (roadmap). Context is capped at 96 bytes.
  • Reach is bounded by the control plane: TMM carries QUIC/DNS/SIP/IPFIX code BNK cannot be told to serve. Traffic arriving ≠ the vulnerable code running.
