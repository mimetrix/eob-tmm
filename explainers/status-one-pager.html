Programmable data plane · status

A verified program, loaded into a running TMM, deciding at a real function entry

The mechanism is proven on a live cluster. What it can mitigate is narrower than the mechanism suggests, and no CVE has been mitigated on traffic — because there is no shieldable CVE inside TMM to mitigate. Both halves are measured, and the second is a property of the CVE population rather than of this design.

Proven · measured on a live TMM

The mechanism works, end to end

  • Loaded into a running process over a socket, signature checked inside TMM OK loaded slot=7 mode=2 signature=verified
  • Armed at a real function entry — no rebuild, no restart OK ARMED LIVE entry=0xcd1004 (no restart)
  • Disarmed, original bytes restored OK DISARMED LIVE
  • Fires once per request on the product's own traffic path 40 requests → fired +40
  • Changes the outcome, one variable — the shield's mode enforce: SAFE_RETURN, survived · monitor: FALLTHROUGH, fatal
  • Reports decisions TMM exposes nowhere — reset cause, file and line, per flow tcp.c:4689 "TCP RST from remote system"
  • Every operation recorded with a kernel-attested asker SO_PEERCRED pid/uid/gid · 47 assertions, 3 suites
  • No layout number written by hand — offsets and addresses derived from the build, gated on build id, and two independent DWARF readers must agree 13 values, readelf ≡ gdb, refuses on mismatch
  • Reproducible from nothing — both machines destroyed and rebuilt, suites green
Bounded · known and quantified

Where the limits actually are

  • Placement is function entry only. A check on a value the function computes cannot be imposed from entry screened 32 findings → 0 read only the arguments
  • Context ceiling is 96 bytes. The TLS/ALPN shield needed 154 and was refused 154: Upper bound must be at most 96 — FALSIFIED
  • Reachability is set by the control plane, not by TMM. TMM carries QUIC, DNS, SIP, IPFIX and APM code the platform cannot be told to serve route kinds served: HTTPRoute · GRPCRoute · TLSRoute
  • Traffic arriving ≠ vulnerable code running. A UDP listener programmed and DNS flowed 10/10, yet the parser was never entered dns_pullup fired +0
  • Four defect shapes are out of reach — under-allocation, use-after-free, in-loop pointer validation, clamp-and-continue
  • Per-call cost on the data path is unmeasured. A floor exists for the program alone; it excludes the trampoline, the call, and cache effects ≤ 11 ns floor — quote as a floor, never as per-packet
Not shown · stated plainly

What we will not claim

  • No CVE mitigated on live traffic. Of the tracked CVEs, essentially none are inside TMM's address space — they are dependency CVEs in other containers. About two are plausible and neither is a shape a shield addresses
  • And a shield does not move a scanner. It does not change the package version, so the finding still reports. For dependencies the right tool is an upgrade
  • Those CVE counts are uncited. The queries behind them were never cached, against this project's own first rule. Marked NOT_RETRIEVED until re-run
  • The vulnerable input is synthesised for the crash/survive pair — the condition is guarded one frame up, so it cannot be produced by configuration
  • One context builder is validated on live traffic, not all. Correct offsets are necessary, not sufficient
  • Who asked is not verified on the wire. Programs are signed; the peer is a process, not a person. The verifying key cannot be revoked
  • The JIT never consults the bounds callback, so interpreter and JIT do not agree on memory safety — and the lab runs the JIT

The accurate framing. Not “CVE mitigation” — on this platform that is a mislabel. Pre-patch mitigation of known-exploitable data-plane defects: a tracked, triaged population in code F5 owns, with a real window between discovery and deployed fix. The nearest demonstrable case has every link confirmed — an entry-derivable bound, an armable hook, and iRules that attach to a live Gateway and run — and three open questions, written down rather than promised away.
