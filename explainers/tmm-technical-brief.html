Embedded userspace eBPF as a third programmability surface in TMM

Link a small verified eBPF VM (uBPF) into TMM and invoke it at designed-in hook points on the fast path. The program reads a typed context and returns a code selecting a host-owned verdict — observe (telemetry) or filter (PASS/DROP/RESET). Every program is statically verified before load (PREVAIL). The core needs no custom helpers and no verifier extension: it's a pure ctx → verdict function; the host owns all state and effects.

engine uBPF (Apache-2.0, x86-64/arm64 JIT, ~150 KB) verifier PREVAIL (eBPF-for-Windows; C++23) invocation in-process, JIT, ~tens of ns; empty hook = 1 branch toolchain clang -target bpf · BTF/CO-RE
§1Invocation model

The VM is a linked library, not an injection technique. At a sanctioned decision/observation site the host calls it inline on the poll loop and acts on the return — no trampoline, no syscall, no kernel trap:

ubpf_exec(vm, &ctx, sizeof ctx, &ret); // ret: 0 PASS · 1 matched/monitor(pass) · 2 matched→DROP // ctx is r1: a typed projection of in-scope state // host maps ret → enumerated outcome and applies it

JIT on hot paths (indirect call into native + the program's handful of insns). The shield chooses among sanctioned outcomes; it cannot synthesize control flow.

§3The ctx contract & shieldability

Each hook exposes its own typed ctx — a curated projection of the state in scope there, authored by the hook's owner (context minimization: TLS secrets / PII / decrypted payload gated). Emitted per build in a signed hook-point map:

{ name, offset, arg_btf, attach_mode, path_class } attach_mode ∈ {observe, filter} path_class ∈ {hot, warm, cold}

Shields resolve by name→offset against the running build; field access is CO-RE-relocated against the build's BTF and fails closed if a referenced field no longer exists. Version-bound, not offset-fragile.

Shieldability is exact — a CVE is runtime-mitigable at a hook iff:

  • the hook executes before the vulnerable operation, and
  • its ctx exposes the field(s) that discriminate the exploit, and
  • a sanctioned outcome leaves TMM consistent (a clean abort branch exists — typically the existing malformed-input/reject path).

No match → not runtime-shieldable at this build → engineering hotfix, or add a hook/ctx next build. The hook-point map — richness & earliness of ctx — is the asset, not any one shield.

§4No helpers, stock verifier core property

Both filter and observe programs are pure functions of ctx — they call nothing. State and effects live host-side, applied around the call:

  • No eBPF helpers to define/register/confine — nothing to confine, sandboxed by construction.
  • PREVAIL used stock — a bounded predicate over a typed ctx is the canonical case; you configure the ctx descriptor, you don't fork the verifier.
  • Anything stateful (rates, timestamps, cross-flow counters) the host computes into ctx.
  • Per-CPU host state on hot hooks → no cache-line contention across core-pinned CMP TMM instances.

Helpers (program writes host maps directly) are an opt-in later tier — they reintroduce the verifier-integration + capability-confinement surface. Not needed for Live Shield or tracepoints.

§5Placement & performance budget
  • Empty hook = one predictable branch. Most CVE shields sit on cold/exceptional paths (the malformed branch) → ~zero steady-state.
  • Hot placement is a measured budget decision, not a ban: per-invocation cost + throughput/latency budget + explicit sign-off. JIT mandatory; per-CPU state mandatory.
  • Watchdog: TMM instance restart within N s of a load → auto-disable that program + alert.
  • Intrinsic in-data-plane cost — a WASM filter or iRule on the same hot hook pays the same order (heavier, for WASM).

Two engines, two verifiers (kernel's built-in vs PREVAIL), one signed catalog + lifecycle; only the enforcement leaf differs. The Cisco Live-Protect analog covers the control plane only.

§7Coverage bound (state honestly)
  • Hardware offload: flows switched/mitigated in ePVA / FPGA (TurboFlex) / crypto, and FastL4 hardware fast paths, never enter TMM software → out of reach of an in-software VM (as for iRules & kernel eBPF). L7/parser/bd classes escalate back into software and stay reachable.
  • Mechanism identical across form factors; coverage varies: VE (no offload) sees the whole data path; appliance carries the offload dead zone; BNK depends on DPU steering vs. what lands in the containerized TMM.
  • Residual dead zone: a crash before the earliest reachable hook (e.g. deep in record parse) → engineering hotfix.
§8Two independent safety obligations
  • Verifier — safe to run: proves bounded execution + memory safety. Load-bearing; nonzero verdict ⇒ reject (fail-closed).
  • Filter contract — safe to take: the decision point sits before any state an abort would unwind; DROP/RESET is an existing reject branch; outcomes are host-enumerated. No bpf_override_return-style synthesized unwind — that skips cleanup/locks/refcounts on a poll loop = corruption.
  • Verified ≠ secure: mandatory signing (checked before the verifier sees bytecode), RBAC/authz tiers, one-way audited exfil sink, attestation/inventory, CRL-style revocation + kill-switch.
§9Lifecycle & HA
  • Device-group object propagated over config-sync → the sync channel is in the trust path; the signature/authorization travels with it.
  • monitor → enforce promotion is change-controlled. Crash-class shields ship enforce-on-arrival (monitor can't be soaked against live crash traffic; FP validation is lab-side).
  • Auto-retire on running_version ≥ fixed_in_version, per member in mixed-version groups. A DROP/RESET is a mitigation, not a health signal — must not mark a pool member/VS down.
§10AI-assisted authoring further direction

Because a shield is a bounded, verifier-proved, host-outcome-selecting program, its worst case is provable — so a generative model can draft one and the verifier is an automatic, fail-closed oracle on the draft (blast radius bounded by proof, not by trust in the model). The model emits a bounded predicate over the signed hook-map/BTF — a constrained IR, never free-form bytecode — iterated against three mechanical gates before a human signs: verifier · exploit-replay · false-positive vs legit corpus. A shieldability classifier returns non-mitigable when no hook's ctx expresses the condition. Human holds the signing key; deployment observe-first + auto-retiring.

§11Open questions / risks gate Phase 3
  • VM-in-TMM stability — the program's single biggest technical risk; watchdog + verifier + cold-path default are the controls. Don't touch TMM's hot path until proven on bd (Phase 1) & control plane (Phase 2).
  • Hook-point-map / BTF drift — hard CI ownership: no build ships without a current map; no shield ships without a resolvable target + field.
  • Toolchain — PREVAIL is C++23 (needs gcc-toolset-13 / modern Boost on the TMOS base OS); uBPF + PREVAIL enter the TCB (consume & harden, not fork).
  • Per-CPU footprint on hot hooks across CMP; offload dead zone messaging vs. AdvWAF virtual-patching & EOB positioning.
