TMM engineering · technical brief · design proposal

A verified, in-data-plane programmability surface for TMM

The AI age collapsed every delivery timeline — new data-plane capability, new instrumentation, and urgent fixes are all expected in hours, not on the release train. Call it the race to zero. It forces two co-equal requirements: runtime security mitigation (block a live threat in place, no release) and runtime programmability (extend what the data plane does — new telemetry and behavior — as verified bytecode against well-defined hooks). Both need one thing TMM offers from nowhere outside: a data-plane surface that is dynamically loadable and provably safe. Embed a verified userspace eBPF VM (uBPF + PREVAIL) at designed-in USDT-style hook points and you have it — observe or enforce, installed in hours under a proof it can't hang or corrupt the poll loop.

§1Problem → requirements

TMOS behavior ships on a release train; the AI age moved everything else to machine speed — new capability, new instrumentation, and urgent fixes all expected in hours. Call it the race to zero: the gap between needing the data plane to change and it changing must shrink toward nothing. It forces two co-equal requirements — two faces of "adapt the running data plane":

forced by the reality → runtime security mitigation + runtime programmability
runtime security mitigation
Block a specific live threat in place, in hours, with no release — a surgical, reversible, vendor-signed control between maintenance windows. (Live Shield.)
runtime programmability
Extend what the data plane does — new telemetry, diagnostics, steering, behavior — as verified bytecode against well-defined hook points (USDT-style), no TMOS rev. Proven-safe installation is what makes it deployable inline. (eob-for-TMM.)

The constraint is the crux: both need a surface that is dynamically loadable AND provably safe, reaching the data plane's own code & internal state. iRules are event/data-model/reachability bound; WASM gives isolation, not a termination proof, and is heavier; kernel eBPF can't see a kernel-bypass TMM. None satisfies all three from outside.

§2The surface — one substrate, two modes

Link uBPF as a library and invoke it at sanctioned hook points inline on the poll loop — a call, not an injection technique. No trampoline, no syscall, no kernel trap:

ubpf_exec(vm, &ctx, sizeof ctx, &ret); // JIT on hot paths // ctx (r1): a typed projection of in-scope state // ret: host maps it to a host-owned outcome, per mode
observe → programmability
Host treats the return as telemetry and never alters flow: tracepoints on in-TMM state (parser machines, conn table, inter-fn latency, error-branch counts), per-flow latency breakdown, flight recorder, targeted capture (tmmdump), steering/tuning signals.
filter → security
Host acts on the return — a host-owned verdict (PASS/DROP/RESET) at a designed-in decision point before the vulnerable op. The Live-Shield CVE mitigation.

Same VM, same hook, same verify gate — only the host's use of the return differs. Enforcement and observability are the two faces of one embedded-eBPF substrate; every hook can start read-only and graduate to a control once trusted.

§4No helpers, stock verifier core property

Both modes are pure functions of ctx — they call nothing; state and effects live host-side, applied around the call:

  • No eBPF helpers to define/register/confine — sandboxed by construction.
  • PREVAIL used stock — a bounded predicate over a typed ctx is the canonical case; you configure the ctx descriptor, you don't fork the verifier.
  • Stateful work (rates, timestamps, counters) the host computes into ctx; per-CPU host state on hot hooks → no cache-line contention across core-pinned CMP instances.

Helpers (program writes host maps directly) are an opt-in later tier; they reintroduce the verifier-integration + confinement surface. Not needed for either mode.

§5The ctx contract — the reach of both modes

Each hook exposes its own typed ctx — a curated projection of in-scope state, authored by the hook's owner (context minimization: TLS secrets / PII / payload gated). Emitted per build in a signed hook-point map:

{ name, offset, arg_btf, attach_mode, path_class } attach_mode ∈ {observe, filter} path_class ∈ {hot, warm, cold}

Resolve by name→offset; field access is CO-RE-relocated against the build's BTF and fails closed if a field is gone. Version-bound, not offset-fragile.

ctx is the reach of both missions — it bounds what you can observe and what you can shield. What a probe can measure, and whether a CVE is mitigable at a hook, are the same test:

  • the hook executes at/ before the point of interest, and
  • its ctx exposes the field(s) that carry the signal / discriminate the exploit, and (filter only) a sanctioned outcome leaves TMM consistent.

The hook-point map — richness & earliness of ctx — is the asset. Design it well and future telemetry and future CVE classes are already reachable; no match → engineering hotfix, or add a hook/ctx next build.

§6Placement & performance budget
  • Empty hook = one predictable branch. Cold/exceptional placements (malformed branch, error path) ≈ zero steady-state.
  • Hot placement is a measured budget decision, not a ban — per-invocation cost + throughput/latency budget + sign-off. JIT + per-CPU state mandatory. Applies equally to hot-path telemetry and per-packet controls.
  • Watchdog: TMM instance restart within N s of a load → auto-disable + alert.

§8Coverage bound (state honestly)
  • Hardware offload: flows in ePVA / FPGA (TurboFlex) / crypto and FastL4 fast paths never enter TMM software → out of reach of an in-software VM (as for iRules & kernel eBPF). L7/parser/bd classes escalate back into software and stay reachable.
  • Coverage varies by form factor: VE (no offload) = whole data path; appliance carries the offload dead zone; BNK depends on DPU steering vs. what lands in the containerized TMM. Mechanism identical across all three.
  • Residual dead zone: a fault before the earliest reachable hook → engineering hotfix.
§9Two independent safety obligations
  • Verifier — safe to run: bounded execution + memory safety; nonzero verdict ⇒ reject (fail-closed).
  • Filter contract — safe to take: decision point before any state an abort unwinds; outcomes host-enumerated; no bpf_override_return-style synthesized unwind (skips cleanup/locks/refcounts on a poll loop = corruption).
  • Verified ≠ secure: mandatory signing (before the verifier sees bytecode), authz tiers, one-way audited exfil sink, attestation/inventory, revocation + kill-switch.
§10Lifecycle & HA
  • Device-group object over config-sync → the sync channel is in the trust path; signature/authz travels with it.
  • monitor→enforce is change-controlled; crash-class shields ship enforce-on-arrival (FP validation lab-side).
  • Auto-retire on running_version ≥ fixed_in_version, per member in mixed groups. A DROP/RESET is a mitigation, not a health signal — must not mark a member/VS down.
§11AI-assisted authoring further direction

A shield is bounded, verifier-proved, and host-outcome-selecting — its worst case is provable — so a model can draft one and the verifier is an automatic, fail-closed oracle on the draft (blast radius bounded by proof, not trust). The model emits a bounded predicate over the signed hook-map/BTF — a constrained IR, never free-form bytecode — iterated against verifier · exploit-replay · false-positive-vs-corpus before a human signs. Same lever applies to auto-generating telemetry.

§12Open questions / risks gate Phase 3
  • VM-in-TMM stability — top technical risk; watchdog + verifier + cold-path default are the controls. Prove on bd (Phase 1) & control plane (Phase 2) before touching TMM's hot path.
  • Hook-point-map / BTF drift — hard CI ownership: no build without a current map; no shield without a resolvable target + field.
  • Toolchain / TCB — PREVAIL is C++23 (gcc-toolset-13 / modern Boost on the TMOS base OS); uBPF + PREVAIL enter the TCB — consume & harden, not fork.
  • Per-CPU footprint across CMP; positioning vs. AdvWAF virtual-patching & EOB; offload dead-zone messaging.
