F5 TMM · design proposal

A runtime, programmable, provably-safe data plane.

In the generative-AI, transformer-based world we live in, everything happens at machine speed. When software needs to change, it needs to change now — a config push, a hot reload, a redeploy, a new feature, a critical security mitigation in minutes. The data plane already flexes at its edges — config, traffic logic — but changing its own code and behavior still waits on a release.

The fix is small and already proven elsewhere: give TMM its own eBPF engine — a verified VM at designed-in hooks — so its code and behavior can change at runtime, provably safely. And because that engine runs where the traffic lives, it does more than close the gap: it turns the data plane into a bespoke data source F5 can use to make the proxy itself smarter.

The data plane touches every flow — decrypted, in context, at line rate — and today that stream is mostly digital exhaust: seen once, used for little more than debug. In the age of AI, that makes it two things at once —

◆ the most defensible layer

Transformers reason in tokens over milliseconds; the data plane moves packets in nanoseconds. Generative AI has nothing to say about line-rate processing — and isn't coming for it.

◆ the most under-used data source

A verified probe turns the exhaust into a unique data source — transforms computed in-situ, on flows no model or endpoint ever sees. Uniquely F5's to develop, and to monetize.

01 one dimension — what it's for

When the world moves this fast, two demands land on the data plane. Functionally, they are the same demand.

The proposal is a surface, not a single feature. Along one axis — what you'd use it for — two co-equal faces stand out. Call it FP²; it's one dimension of a wider payoff.

FP Flexible Programmability

Extend what it does.

New telemetry, new logic, new behavior in the running data plane — a metric you didn't think to collect, a diagnosis, a tuning decision — delivered against designed-in hook points, no rebuild.

FP Flexible Protection

Mitigate what's live.

Block a specific, active threat in place, in hours, with no release — a surgical, reversible control that holds the line until the patched build ships on its normal schedule.

FP Flexible Programmability × FP Flexible Protection = FP2

Two co-equal faces, both of the form Flexible P—, so it squares. One verified surface delivers both: change the running data plane's behavior — safely, now.

02 a double-edged sword

TMM is fast because it left the kernel behind. That's exactly why it's so hard to change.

TMM is a kernel-bypass microkernel: its own network stack, its own memory manager, a core-pinned poll loop that never syscalls for traffic. That architecture is why it's fast — and why it's opaque and rigid.

The industry's answer to safely changing a running system is eBPF in the kernel. But TMM bypassed the kernel — so kernel eBPF is structurally blind to everything TMM does with the traffic. Today, changing TMM's own code means the slow lane, every time:

change today C source → rebuild → re-qualify → release train weeks–quarters

◆ data plane

Own stack, poll loop, plugin processes (bd, the WAF/ASM engine). Kernel-bypassed.

Say it plainly: TMM is a kernel. Its own scheduler, its own memory manager, its own network stack — it plays every role Linux plays for the traffic it carries. Linux earned an eBPF VM inside it for exactly this job; a kernel of TMM's standing and maturity deserves its own eBPF hosting VM. That's the move.

03 the move

Give TMM — a microkernel — its own eBPF.

It's entirely buildable, because what makes kernel eBPF safe was never the kernel: it's a static verifier and a small sandboxed VM. The verifier analyzes the bytecode and proves — before it ever runs — that the program is bounded (every path terminates in a known number of steps; it cannot loop forever, so it can never hang a poll loop) and memory-safe (every load and store stays inside the bytes it was handed; it cannot read what it wasn't given or scribble on TMM's memory). Both are libraries. Neither needs the kernel.

So bring them inside. Embed a small userspace eBPF VM — uBPF, ~150 KB, JIT-compiled — inside TMM's own address space, at designed-in hook points, gated by a stock verifier (PREVAIL). Now behavior arrives as bytecode, proven safe before it loads. No rebuild. No reboot. The data plane gets a fast lane:

change todayC source → rebuild → re-qualify → release trainweeks–quarters
the proposalauthor → clang → PREVAIL verify → sign → loadhours

The hook surface needn't start from a blank page, either: a candidate catalog of USDT tracepoints can be drawn up alongside the engine — L3/L4 ingress and the connection table, the TLS record layer, the L7 parsers, bd/WAF internals, the poll loop itself. Each hook that lands adds one more place to observe, one more place to act.

the whole proposal, in three words

runtime· programmable· provably safe

Three properties, equal weight — and nothing else brings all three in-process, at the data plane:

iRules runtime, but never provably safe
DynaD runtime too — a Lua-based earlier swing at exactly this, since deprecated
WASM programmable, but bounded by a runtime kill — not a proof
kernel eBPF provably safe, but in the wrong kernel — a USDT lets it watch TMM, not act inside it, and traps on every hit

This is the only surface that is all three, in-process — reaching the data plane's own code and state.

Complementary, not a replacement. F5 has a long history of extending programmability into the runtime data plane — iRules stays the first line for traffic logic, WASM the home for rich extensions. This reaches the layer none of them can, and modernizes that lineage for the AI age.

04 one surface, both faces

Program and protect are the same machinery. Only the last step differs.

A program in its simplest shape reads a curated context and returns a value — the engine can do far more, but this base shape is all the symmetry needs. Whether that value becomes a recorded metric or an enforced verdict is the host's choice — not a different mechanism.

You'd author one with tmmtrace, a proposed front-end — bpftrace for TMM: from a one-liner to a full multi-probe script, it compiles to eBPF bytecode, clears the verifier, and — once signed — attaches at the named hooks. And it spans both planes: point it at a data-plane hook and it runs in TMM's embedded VM; point it at a control-plane daemon and it rides kernel eBPF. Each probe has three parts:

tmm:<stage>:<event> /predicate/ { action } which hook · tmm: / ctl: when it fires what to do

Same program shape; the host records the return. This is observability — deep telemetry from inside a black box, on demand, then off. Same program shape; the host acts on the return. This is enforcement — here, dropping the frame the program matched.

Nothing about the VM, the verifier, or the context changed — only what the host does with the answer. That symmetry is the thesis: one verified surface, serving programmability and security as equals.

And read-a-context, return-a-value is just the floor. The hook surface is designed to grow — a widening catalog of designed-in USDTs, each new context field opening more of the data plane to both observation and control, with room to give programs more power over time.

05 what the engine unlocks

A general-purpose platform — with one flagship security application.

Most of what the engine is for isn't security at all — it's everyday programmability and observability inside the data plane:

  • Deep observability. Counters, latency histograms, and a flight recorder from inside a kernel-bypassed data plane — summarized with tmmtrace (bpftrace for TMM) or captured byte-for-byte with tmmdump (tcpdump for TMM).
  • A data source, tapped. Verified transforms computed where the data lives — refining the proxy's digital exhaust into signals and products only F5 is positioned to build.
  • New logic, telemetry & tuning. Behavior and metrics shipped as bytecode, no TMOS rev; read internal load and nudge a knob.
  • Field diagnostics. Ship a signed probe to characterize a production issue in situ, then pull it — no debug build, no core-dump archaeology.
  • AI-authored programs. Because safety is a proof, not trust, a model can draft one and the verifier is a fail-closed acceptance gate — blast radius bounded before a human signs.

Then there's the flagship: the shield. One specific application, built on the enforce primitive plus the governance a security control demands — a signed, CVE-keyed catalog, monitor→enforce modes, and auto-retirement when the patched build lands. It mitigates a live exploit — in TMM or the control-plane daemons — that no iRule, WAF rule, or kernel probe reaches. An app on the platform, not the platform itself.

06 the flywheel · at fleet scale

Point the same probe at the data, and the proxy becomes AI's sensory organ.

TMM terminates TLS: it sees every flow — decrypted, in context, at line rate, a vantage no endpoint or network sensor has. That value has stayed locked away — you can't export decrypted line-rate traffic (bandwidth, privacy, law), and you couldn't compute on it in place. The verified substrate opens both locks: a transform runs where the data lives and exports only the distilled signal, never the payload — the program has no other way out. The stream you used to throw away becomes raw material for new products:

  • See the blind spots. A live API inventory and sensitive-data-exposure map; malware beaconing and exfil in decrypted server-side traffic that on-the-wire network-detection tools (NDR), stuck looking at ciphertext, physically cannot see.
  • Detection that learns. Behavioral baselines that flag zero-day behavior; a shield factory tuned on real fleet traffic instead of synthetic corpora.
  • A model only F5 can train. The model that has seen more real application-layer traffic than anything on earth — powering detection, tuning, and new capabilities across the whole fleet, on data no competitor can source.

Only the distilled features leave the box — the payload never does, and the model never touches the data path.

And the leverage is the install base, pointed inward. F5 already sits in the path for a large share of the world's enterprise application traffic — not a sensor network to build, one already deployed and switched on by a software capability. Federated across that fleet, every box makes the model better and the model makes every box better: sharper zero-day detection, self-tuning, fewer false positives, whole new capabilities shipped as verified programs. That's a compounding product moat a latecomer can't buy — catching up needs both the placement and the years of traffic. The play is to keep the intelligence in the product — using it to build a proxy no one can match.

And the loop is safe to close. The model authors new verified programs that load back into the plane — proven safe, the model never in the trust path — so the flywheel turns without an unvetted model ever touching the data path. And because the signal leaves while the payload can't, F5 can build on data at a regulated TLS boundary where everyone else is forbidden even to collect it.

07 under the hood · for the engineers

How the programmable data plane works.

Everything above rests on one small, in-process call, gated by a static proof. Here's the machinery — the call, where it sits, why it's safe to run inline, and how the surface grows.

7.1 The engine & its hook points

What's embedded in TMM is a full in-process eBPF engine — a JIT-compiled VM that runs arbitrary verified bytecode — not a single-purpose gate. A hook point is a named spot in TMM's own source, placed by F5's engineers, where that engine runs a program over a curated view of the code's local state. The same machinery feeds counters, latency histograms, and flight-recorder rings for deep observability, drives steering and self-tuning decisions, and — where the host wants one — returns a value it acts on. That last mode is what a shield specializes; returning a decision is one thing the engine does, not the point of it.

Designed-in is the operative word: because F5 owns the source, hooks are deliberate, named, versioned insertion points published in a per-build map — not fragile offsets an external tool guesses at and rewrites into a running process. A hook with nothing attached costs about one predictable branch (dark until lit); attach a signed program and it runs right there, in-process — cold path, or hot on a measured budget.

// at a hook point in TMM: pack a curated snapshot, run the VM struct l7_ctx ctx = { .opcode = f->opcode, .len = f->len }; ubpf_exec(vm, &ctx, sizeof ctx, &ret); // ret is the program's result; the host decides what it means: // a sample → recorded as a counter, histogram, or ring // a code → acted on — e.g. a shield's pass / drop / reset

The ctx is the program's entire world — it's input; what the return means is the host's choice — a sample to record, or a code to act on. In the base tier, programs are pure functions of ctx — they read fields and return a number, and call nothing; the host owns the counters, histograms, rings, and any decision logic around the call. Two consequences fall out, and they erase the hardest parts: no custom helpers to define, register, or secure; and stock PREVAIL — a bounded predicate over a typed context is the canonical case the verifier already proves, so there is no fork in the trust path.

7.2 Placement — two planes, two engines, one catalog

A single mechanism can't cover TMOS, because TMOS is two execution environments. The plane decides the engine.

PlaneWhat runs thereEngine
ControlLinux daemons — httpd, tmsh, MCPD; iControl REST on the JVM kernel eBPF / uprobe · + JVMTI for Java
DataTMM microkernel + plugin processes (bd/WAF) — kernel-bypassed embedded uBPF (+ PREVAIL)

The control plane reuses the kernel's own verifier; the data plane is the crown jewel, where an in-process VM is the only thing that can reach inside TMM's own execution. Either way, one front-end drives both: you author with tmmtrace against a hook by name, and its namespace picks the engine — a ctl: hook compiles to kernel eBPF (kernel verifier), a tmm: hook to embedded uBPF (PREVAIL). One DSL, two engines, one trust path — retarget a program from a TMM parser to an httpd request path by changing only the hook name.

7.3 Three form factors — same mechanism, honest coverage

Appliance, VE, and BIG-IP Next all run the same TMM, so the mechanism is identical. Coverage is not — it scales inversely with how much the platform offloads to hardware.

Form factorData pathCoverage
BIG-IP VEpure software, no offloadfull — the VM sees the entire path
ApplianceePVA / FPGA / TurboFlex offloadsoftware path only — offloaded flows are a hardware boundary
BIG-IP Next (BNK)containerized TMM, DPU-dependentdepends on how much the DPU steers vs. lands in TMM

Honest boundary: a flow handled entirely in silicon never enters TMM software, so an in-TMM hook can't see it — the same limit iRules and kernel eBPF already have. The L7/parser stages and bd/WAF internals worth reaching execute in software regardless, so they stay in view.

7.4 Why it's safe to run inline

Start with the load-bearing assumption, named plainly: every claim on this page leans on the verifier being right. Three reasons that's a strong bet. Provenance — PREVAIL is the verifier Microsoft ships in eBPF-for-Windows: built on abstract interpretation, a formal method rather than hand-grown heuristics, publicly maintained and hardened in production. Narrow envelope — this design uses it at its best-proven case: a bounded predicate over a small typed struct, no helpers, no maps. Depth — it is not the only gate: only F5-signed bytecode ever reaches it, and a per-hook watchdog stands behind it. Trust the proof; don't depend on it alone.

The second principle is just as blunt: verified ≠ secure. PREVAIL proves a program can't crash or hang TMM; it proves nothing about intent. Security is the governance around the VM:

  • Proven before load — bounded memory + termination, or it's rejected (fail closed).
  • Signed & authorized — signature checked before the verifier sees bytecode; enforce needs stricter authz than observe; RBAC-gated.
  • Host-owned outcomes — a program only returns a value; everything done with it, the host does. Even at an enforce point, the return merely selects among outcomes the host code already owns (a shield's pass / drop / reset, for example); a program cannot invent control flow or force an arbitrary early return.
  • Context minimization — the signed hook-point map declares, per hook, exactly which ctx fields are exposed; secrets and PII are withheld by default.
  • One-way egress — with no helpers a program has no I/O of its own; it returns a value to a host-owned, schema-checked sink it cannot read back or redirect. Only host-approved derived output leaves, never raw payload — the composition (verifier: no exit + reads only declared fields; host: the one exit takes only the schema) that underwrites the §6 data-plane-intelligence privacy claim.
  • Governed lifecycle — attestation/inventory, tamper-evident audit, instant kill-switch + revocation, and a per-hook perf budget with a watchdog.

7.5 Lifecycle — nothing outlives its purpose

Every program is authored, proven, signed, loaded — and can carry an expiry, so nothing outlives its purpose: a diagnostic probe when its window closes, a security shield when the patched build lands. No zombies.

author (human or AI-assisted)→ clang → bytecode→ PREVAIL verify→ sign→ load → run→ auto-retire

7.6 The surface is built to grow

Read-a-context, return-a-value is the floor — chosen for maximal safety, not the limit of the VM. Two growth paths, deliberately different in cost:

  • More hooks — for free. Each release can add USDTs (define a ctx, place a hook, publish it in the signed map) with no VM, verifier, or helper work. Every new field widens what can be observed and enforced, so the instrumentation surface compounds over time.
  • Helpers — if and when needed. Richer, stateful programs (direct host-map access, cross-flow state) can be enabled later through an optional helper tier. The honest trade: helpers reintroduce an ABI to secure and verifier surface to manage — which is exactly why the base ships without them and stays on stock PREVAIL. Power is available; safety stays the default.
