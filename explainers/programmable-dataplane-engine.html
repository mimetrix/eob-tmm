F5 TMM · design proposal

A runtime, programmable, provably-safe data plane.

Whoever shortens the distance from code commit to code deployed wins. That is the whole game in software, and a data plane is where it is hardest. TMM — F5's Traffic Management Microkernel, the process that carries the traffic — already changes its behaviour at runtime through several surfaces: a config push, a profile change, a web-application-firewall (WAF) policy update, traffic logic in an iRule, and a WASM extension surface arriving for the same purpose — but each acts on the curated traffic model the proxy chose to expose, at the events it chose to fire. A change that has to reach the code's own internals — a parser's error branch, a plugin handoff, a counter or steering decision at a stage the model does not expose, the condition behind a crash — has exactly one path, and it is a build.

The fix: give TMM its own eBPF engine — one verified engine, resident at a single address in the process, reached from any function entry the build already emitted — so its code and behavior can change at runtime, provably safely. One general-purpose surface: load a program, prove it safe, run it in-process — no rebuild, no reboot, no release train. (The engine ships in one enabling build. After that, every program — every probe at a boundary that build exposes — is a load.)

The data-plane mechanism described here now runs on a live TMM: a shield is loaded over a socket into an already-running process, armed at a function entry while traffic flows, and disarmed — no rebuild, no restart. Where the page still reads “would”, treat the mechanism as built and the outcome as not yet shown.

Built since this page was written. Signature verification is no longer part of the proposal — an Ed25519 signature over the program's binding is checked inside TMM before admission, and unsigned, re-signed and altered programs are refused. The hook index is generated per build, so a hook is named rather than addressed, and arming is refused when the index and the running binary disagree.

Still genuinely unproven, and conditional throughout. No CVE has been mitigated on live traffic — the mechanism is shown, the outcome is not. The per-call cost of an armed hook on the data path is unmeasured. A floor exists: a small program executes in ≤ 11 ns on the compiled path, and that figure is bounded by the timer measuring it rather than by the program, so it excludes the trampoline's register save and restore, the call and return, and cache effects under real traffic. Quote the floor as a floor and nothing as a per-packet cost.

And the perimeter moved rather than closed. The loader authenticates the program, not the caller: anything able to reach its socket may ask, the verifying key is compiled into the binary with no revocation path. Every operation is recorded as of 2026-08-20 — one line each, carrying the op, its target, the program's hash, the build ID of the binary that served it, and the verdict the caller received verbatim — and the asker is the pid and uid the kernel reports for the connecting process, which cannot be forged and is still a process rather than a person. That gap — an identity, not a record — is what still makes this lab-only.

01 the holdout

TMM is fast because it left the kernel behind. That's exactly why it's so hard to change.

TMM is a kernel-bypass microkernel: its own network stack, its own memory manager, its own scheduler — a core-pinned poll loop that never syscalls for traffic. That architecture is why it's fast — and why it's opaque and rigid.

The industry's answer to safely changing a running system is eBPF in the kernel. But TMM bypassed the kernel. Kernel eBPF can attach to TMM — a uprobe on the tmm binary works today — but it can't afford to (every hit traps into the kernel, inside a run-to-completion loop) and it can't enforce (the kernel forbids overriding a return from a uprobe). So it can watch, expensively, and never act. Today, changing TMM's own code means the slow lane, every time:

change today C source → rebuild → re-qualify → release train a release

Say it plainly: TMM is its own kernel. It plays every role Linux plays for the traffic it carries. Linux earned an eBPF VM inside it for exactly this job; a kernel of TMM's standing and maturity deserves its own eBPF hosting VM. That's the move.

And a proxy is the favorable shape for this — but read it as three budgets, not two. Per request: microseconds, because TMM terminates TCP, negotiates TLS, parses L7 and evaluates policy — a hook costing tens of nanoseconds is noise. Per packet inside the proxy path (TCP reassembly, TLS records, L7 framing): hundreds of nanoseconds, so a hook is a few percent — affordable with measurement and sign-off, not free. A pure FastL4 fast path (L4-only forwarding that skips the proxy machinery): tens of nanoseconds, where the objection that keeps bytecode out of packet forwarders applies to us too. A forwarder only ever has that third budget. The middle tier is the one that matters, because the pre-L7 stages worth reaching — fragment reassembly, TCP state, record-layer parsing — run there, before any request exists. A proxy also has deep internal state worth looking at, which is what makes a curated context valuable here rather than trivial.

02 the move

Give TMM — a microkernel — its own eBPF.

It's entirely buildable, because what makes kernel eBPF safe was never the kernel: it's a static verifier and a small sandboxed VM. The verifier analyzes the bytecode and proves — before it ever runs — that the program is memory-safe (every load and store stays inside the bytes it was handed; it cannot read what it wasn't given or scribble on TMM's memory) and, with its termination check switched on — off in PREVAIL's default configuration — bounded: no path can loop forever. Both are libraries. Neither needs the kernel. Termination isn't the whole of hot-path safety — a per-hook time budget handles the rest (§5.4); the verifier is the floor, not the ceiling.

So bring them inside. Embed a small userspace eBPF VM — uBPF, ~150 KB, compiled just-in-time (JIT) to native code — inside TMM's own address space — once, in one place — gated by a stock verifier (PREVAIL). The engine does not move to the code it inspects: a single trampoline sits between them, and arming a function rewrites that function's entry to call it. What differs per hook is a slot — a program, a mode, a counter — not another engine. Now behavior arrives as bytecode, proven safe before it loads. No rebuild. No reboot. The data plane gets a fast lane:

change todayC source → rebuild → re-qualify → release traina release
the proposalauthor → clang → PREVAIL verify → budget pass → sign → loaddays

Bytecode plus a verifier doesn't delete the test–certify–apply pipeline; it re-proportions it. Testing shrinks because the outcome set is bounded by construction, not because the verifier says so. Certification barely shrinks — what speaks to an evaluator is the signature, an established construct. Applying is where the artifact property does the work: a load is not an image install.

And the mechanism isn't hypothetical. Microsoft's eBPF-for-Windows ships this pair — uBPF as the execution engine, PREVAIL as the verifier — in a maintained, production-used component. The verifier half is the well-trodden part; the JIT is where we do our own hardening (§5.4). A userspace VM running verified bytecode at a host-owned hook is an established pattern; what's new is bringing it to a proxy data plane that hasn't had it. The parts we'd build are the parts that are ours anyway: the hooks, the host-owned outcomes, and the signing gate.

And the hooks map onto structures TMM already has — and new ones it will define, not a blank page. A candidate catalog of USDT tracepoints (userland statically-defined tracing — named probe points designed into the source) can be drawn up alongside the engine, right where that state already lives: L3/L4 ingress and the connection table, the TLS record layer, the L7 parsers, the plugin processes, the poll loop itself.

Three properties, equal weight — and nothing else brings all three in-process:

iRules runtime, but not provably safe
DynaD runtime too — an earlier scripting-based swing at this, since deprecated. The difference: an unverified script had no proof, no signing gate and no host-owned outcome set — the three things that make this one governable
WASM programmable, but its guarantees are enforced dynamically — bounds-checked as it runs, time bounded by a counter that aborts. eBPF proves the same properties before load; both still need a runtime time guard (§5.4)
kernel eBPF provably safe, but in the wrong kernel — a USDT lets it watch TMM, not act inside it, and traps on every hit

An embedded eBPF engine is the only surface that is all three, in-process — reaching the data plane's own code and state.

Complementary, not a replacement — and the dividing line is sharper than "iRules see the traffic model, eBPF sees the code". iRules and WASM survive the poll loop by coarse placement, by suspend-and-resume when a rule has to block, and ultimately by a watchdog that restarts TMM: they manage that risk and accept what is left, where a static proof, an admission-time cost bound and fuel are a strictly stronger position. What eBPF gives up in exchange is not small — a verified program cannot yield. No blocking, no sideband call, no cross-blade lookup, architecturally rather than as a deferred tier. So anything that must wait belongs in an iRule or a WASM filter; anything that must be provably bounded belongs here. That is the division of labour, and it modernizes the lineage.

03 one shape · observe · act

Observe and act are the same machinery. Only the last step differs.

First, what a program is. Not a process that runs on its own — a small event handler the engine invokes at a hook, triggered by the very thing it's watching: execution reaches that point in the code, the program fires, and it is handed a curated context describing what's there. In its simplest shape it reads that context and returns a value — the engine can do more, but that base shape is all the symmetry needs. Whether the host records that value as a metric, uses it to stream a window of live internal state out to userspace — for discovery, debugging and root-cause analysis (RCA) — or treats it as a decision to act on is its choice, not a different mechanism.

So how would you write one? You write a few lines of C and compile with clang -target bpf — or, for one-line probes, tmmtrace, a proposed authoring front-end that emits the same bytecode: bpftrace for TMM. It compiles the probe to bytecode, verifies it and, once signed, attaches it at the named hook — one line or a full multi-probe script, same path.

One grammar can reach both planes — a tmm: hook runs in TMM's embedded VM, a ctl: hook rides kernel eBPF (§5.2) — but only the first half is net-new, and that is why the tool is named for TMM. On the control-plane daemons, kernel eBPF is already shipped and bpftrace already authors for it, so the ctl: side is convenience over an existing path. The TMM side is the part nothing in existence can do. Each probe is three parts:

tmm:<stage>:<event> /predicate/ { action } which hook · tmm: / ctl: when it fires what to do

The action is the only part that decides observe vs. act. Same hook, same predicate — flip the verb:

Same program shape; the host records the return. This is observability — deep telemetry from inside a black box, on demand, then off. Same program shape; the host acts on the return. This is control — here, steering the flow the program flagged toward a healthier pool member.

Nothing about the VM, the verifier, or the context changed — only what the host does with the answer. That symmetry is the thesis: one verified surface, serving observation and control as equals. And it is the floor, not the ceiling: the hook surface is built to grow (§5.6).

04 what the engine unlocks

A general-purpose programmability platform for the data plane.

One engine — a verified program running at a hook — covers a wide span of everyday programmability and observability inside a black box:

  • Deep observability. Counters, latency histograms, and a flight recorder from inside a kernel-bypassed data plane — summarized with tmmtrace or captured byte-for-byte with tmmdump: proposed front-ends, bpftrace and tcpdump for TMM.
  • New logic, telemetry & tuning. Behavior and metrics shipped as bytecode, no TMOS rev — a metric you didn't think to collect, or reading internal load to nudge a knob.
  • In-path control. Steer, sample, rate-limit, or gate a flow on an internal signal — the decision computed right at the hook, inline, with no round-trip out of the data path.
  • Field diagnostics. Ship a signed probe to characterize a production issue in situ, then pull it — no debug build, often no waiting for a repro. It complements post-mortem analysis: a probe only answers a question someone already thought to ask, and a core dump is the fallback for when nobody did.
  • Runtime CVE mitigation. Recognize a bug's precondition and take a host-owned safe outcome in the window before a patched build is installed. Two assumptions carry that, and both are arguable: that an operator cannot always install one immediately, and that enough real advisories are reachable from a surviving function boundary at all — nobody has yet checked published ones one by one. Traced end to end, with its limits, in the CVE walkthrough. It is one use of the engine, and the narrowest: it needs the same hooks, verifier and signing gate as everything above it.
  • AI-authored programs. Because safety is a proof, not trust, a model can draft one and the verifier is a fail-closed acceptance gate — blast radius bounded before a human signs.

Every one of these is the same engine — a verified program at a hook; they differ only in what the host does with its result. A new capability ships as verified bytecode, then retires — not as a TMOS release.

05 under the hood · for the engineers

How the engine works.

Everything above rests on one small, in-process call, gated by a static proof. Here's the machinery — the call, where it sits, why it's safe to run inline, and how the surface grows.

5.1 The engine & its hook points

What's embedded in TMM is a full in-process eBPF engine — a JIT-compiled VM that runs arbitrary verified bytecode — not a single-purpose gate. It is linked in once and stays at one address. A hook point is a named place the engine can be reached from; nothing about the engine is replicated there. Arming a hook rewrites that spot to call one shared trampoline, which builds a curated view of the code's local state, runs the program registered for that hook, and applies the return. What exists per hook is a slot — a program, a mode, a counter — not another engine. The same machinery feeds counters, histograms and flight-recorder rings, streams captured state out to userspace for RCA, and drives steering and self-tuning where the host wants to act on the return.

Two kinds of hook — the anticipated and the unanticipated. The first is a designed-in tracepoint (a USDT): F5 places a named, versioned point exposing a curated ctx — a stable contract, published in a per-build map. That is the planned surface, and it is where the standing value lives: the metrics, histograms and latency breakdowns you want on every box, whose meaning holds across releases. But no catalog anticipates every question someone will need to ask three years from now — which is what the second kind is for.

The second is a function-boundary probe: attach at the entry or return of an existing named function — any function that survived the build as its own out-of-line body — reading that function's arguments, resolved by the host into the ctx. It rides the code's existing structure — functions and their signatures — so you can instrument a spot nobody thought of ahead of time, with no new build, and the engine answers questions it was never designed for: why is this one customer's TLS renegotiation path slow, which flows are reaching a code path we thought was unreachable — and, as one case among those, recognising the precondition of a bug nobody foresaw. (The mechanism is the kernel's own fentry/ftrace trampoline model, applied to TMM's own functions.)

Both are built in, not injected. F5 owns the source and the symbol table, compiles the hook capability in (patchable function entries), and attaches at a named symbol, not offsets an external tool guesses at in a foreign process. A hook with nothing attached is dark until lit. And the honest bound on reach: which functions are hookable is decided by the optimiser, not by us. At -O2 an inlined or identical-code-folded function has no entry pad of its own, and a cloned one (.constprop, .isra) changes both its symbol name and its argument list. So the hookable set is whatever the build's signed hook map says it is — a subset of the source, derived from the build's own debug information, which is the least-proven engineering assumption here. Pinning a specific function in means marking it noinline: a source change, with its own cost.

The honest trade is stability: a tracepoint's ctx is a curated, versioned contract; a function-boundary probe's is build-specific (function X's signature at build Y) — more reach, a looser contract, re-validated per build. Either way it is verified, signed, and budgeted before it runs.

// the hook is not code. It is the function's own entry, rewritten in place: // f3 0f 1e fa endbr64 // e8 f0 6c 75 ff call ls_trampoline_entry <- was 5 NOPs // the trampoline — ONE of these, shared by every armed hook uint64_t ls_trampoline(struct hook_slot *slot, ...) { struct l7_ctx ctx = { .opcode = f->opcode, .len = f->len }; // curated snapshot uint64_t ret = slot->fn(&ctx, sizeof ctx, stack, stack_len); } // ^ native code, JIT'd once at load. // No bytecode is walked per call. // ret is the program's result; the host decides what it means: // summarize → recorded as a counter, histogram, or ring // capture → a window of state streamed out to userspace (RCA, debug) // act → a decision from the host's set — e.g. steer / drop

The ctx is the program's entire world, and it is a per-core copy, discarded on fall-through: the host's builder walks TMM's structures in native C and hands over resolved scalars, so a program never chases a pointer. What the return means is the host's choice. In the base tier, programs are pure functions of ctx — they read fields and return a number, and call nothing; the host owns the counters, histograms, rings, and any decision logic around the call. Two consequences fall out, and they erase the hardest parts: no custom helpers to define, register, or secure; and stock PREVAIL — a bounded predicate over a typed context is the canonical case the verifier already proves, so there is no fork in the trust path.

5.2 Placement — two planes, two engines, one catalog

A single mechanism can't cover TMOS, because TMOS is two execution environments. The plane decides the engine.

PlaneWhat runs thereEngine
ControlLinux daemons — httpd, MCPD; iControl REST on the JVM; iControl LX on Node kernel eBPF / uprobe · + JVMTI · + V8
DataTMM microkernel — kernel-bypassed (plugin processes are ordinary Linux processes) embedded uBPF (+ PREVAIL)

The control plane reuses the kernel's own verifier; the data plane is the crown jewel, where an in-process VM is the only thing that can reach inside TMM's own execution affordably, and act on what it finds. Either way, one front-end can drive both: you author with tmmtrace against a hook by name, and its namespace picks the engine — a ctl: hook compiles to kernel eBPF (kernel verifier), a tmm: hook to embedded uBPF (PREVAIL). It is named for TMM because that is the half that needs it: bpftrace already authors for kernel eBPF, so reaching ctl: from the same grammar is convenience, not capability. (Not one binary for both: a different engine means a different ctx and a different verifier, so retargeting is a re-author, not a rename.)

5.3 Three form factors — same mechanism, honest coverage

Appliance, VE, and BIG-IP Next all run the same TMM, so the mechanism is identical. Coverage is not — it scales inversely with how much the platform offloads to hardware.

BIG-IP VEpure software, no offloadfull — the VM sees the entire path
Applianceoffload to the ePVA flow accelerator, FPGA/TurboFlexsoftware path only — offloaded flows are a hardware boundary
BIG-IP Next for Kubernetescontainerized TMM, fronted by a DPU (SmartNIC)depends on how much the DPU steers vs. lands in TMM

Honest boundary: a flow accelerated end to end never enters TMM software, so its contents are invisible to an in-TMM hook — the same limit iRules and kernel eBPF already have. But the offload boundary is ordinary TMM software and hookable on both sides — the accelerate/escalate decision, the escalation return, the error paths — while the L7/parser stages and plugin processes run in software regardless. Only a fault inside the silicon needs a firmware fix.

5.4 Why it's safe to run inline

Start with the assumption every claim on this page leans on: the verifier being right. Three reasons that's a strong bet. Provenance — PREVAIL is the verifier Microsoft ships in eBPF-for-Windows: built on abstract interpretation, a formal method rather than hand-grown heuristics, publicly maintained and hardened in production. Narrow envelope — this design uses it at its best-proven case: a bounded predicate over a small typed struct, no helpers, no maps. Depth — the JIT emits native code inside TMM, so an unsound verifier would mean arbitrary code in the data plane, and that is what a security review will press hardest. But only bytecode F5 authored ever reaches the verifier — it runs in F5's admission pipeline, before signing, never on the box — and only F5-signed bytecode ever reaches the in-TMM JIT. Attacker-controlled input never touches either, so a soundness bug is not a traffic-borne RCE — remote code execution triggered purely by sending traffic through the data path, needing no credentials and no management-plane access — but a supply-chain concern, gated by signing-key protection. Trust the proof; don't depend on it alone. (The hard problems are catalogued in the engineering register.)

The second principle is just as blunt: verified ≠ secure, and verified ≠ correct. PREVAIL proves a program is memory-safe, and terminating where that check is enabled — not that it fits the hook's budget, and nothing about intent. Time-safety and security both live in the governance around the VM:

  • Proven before load — bounded memory + termination, or it's rejected (fail closed).
  • Bounded in time, not just in steps — a proof that a program terminates is not a worst-case execution time (WCET): the longest it can take on the hardware. So each hook adds an instruction-budget ceiling at load and a runtime guard as it runs — a provably-terminating program still can't overrun its hook's budget (the guard's mechanism is the register's §01 open question). The budget is set per invocation and gated by the hook's rate — per packet, per connection, per request — not by one global number.
  • Signed & authorized — the box checks the signature before the JIT sees bytecode (the verifier already ran, at F5); a program that acts needs stricter authorization than one that only observes, and role-based access control gates who may load it.
  • Host-owned outcomes — a program only returns a value; everything done with it, the host does. Even at an acting hook, the return merely selects among outcomes the host code already owns (steer / drop / sample, from the canonical set); a program cannot invent control flow or force an arbitrary early return.
  • Context minimization — the signed hook-point map declares which ctx fields each hook exposes; secrets and personal data are withheld by default.
  • One-way egress — with no helpers a program has no I/O of its own: it returns a value to a host-owned, schema-checked sink it cannot read back or redirect, and the verifier proves it reads only its declared ctx fields. Only host-approved derived output ever leaves, never raw memory.
  • Governed lifecycle — attestation/inventory, tamper-evident audit, a kill-switch and revocation, a per-hook perf budget with a watchdog, and a control-plane canary that auto-unloads on a health signal — because a verified, signed program can still be wrong (black-hole or misroute traffic); the proof bounds crashes, the canary bounds bad-but-valid programs.

5.5 Lifecycle — nothing outlives its purpose

Every program is authored, proven, signed, loaded — and can carry an expiry, so nothing outlives its purpose: a diagnostic probe when its window closes, a temporary control when it is no longer needed.

author (human or AI-assisted)→ clang → bytecode→ PREVAIL verify→ budget pass→ sign→ load → run→ auto-retire

5.6 The surface is built to grow

Read-a-context, return-a-value is the floor — chosen for maximal safety, not the limit of the VM. Two growth paths, deliberately different in cost:

  • More hooks, cheaply. Each release can add USDTs (define a ctx, place a hook, publish it in the signed map — each rides a build), and function-boundary hooks come with the compiler flag — no VM, verifier, or helper work either way. Honest cost: the flag pads every function entry in the image, so there is a one-time build-time footprint (i-cache/size) paid whether or not a hook is ever armed — a number to measure before committing, not to assume. Every new field widens what can be observed and acted on, so the surface compounds.
  • Helpers — if and when needed. Richer, stateful programs (direct host-map access, cross-flow state) can be enabled later through an optional helper tier. The honest trade: helpers reintroduce an ABI to secure and verifier surface to manage — which is exactly why the base ships without them and stays on stock PREVAIL.
