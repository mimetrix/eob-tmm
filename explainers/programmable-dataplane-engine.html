F5 TMM · design proposal

A runtime, programmable, provably-safe data plane.

Two clocks, running at very different speeds. Vulnerability discovery and exploit tooling now move at machine speed; a data-plane release train moves in weeks, deliberately, because that cadence is what certification and quality discipline cost. The gap between those two clocks is the problem — not F5's release cadence, which is doing its job. The data plane already flexes at its edges — a config push, a policy change, traffic logic in an iRule — but changing its own code and behavior has exactly one path, and it is a build.

The fix: give TMM its own eBPF engine — a verified VM at designed-in hook points — so its code and behavior can change at runtime, provably safely. One general-purpose surface: load a program, prove it safe, run it in-process — no rebuild, no reboot, no release train. (The engine ships in one enabling build; after that every mitigation — and every probe at a boundary that build exposes — after that is a load.)

01 the holdout

TMM is fast because it left the kernel behind. That's exactly why it's so hard to change.

TMM is a kernel-bypass microkernel: its own network stack, its own memory manager, its own scheduler — a core-pinned poll loop that never syscalls for traffic. That architecture is why it's fast — and why it's opaque and rigid.

The industry's answer to safely changing a running system is eBPF in the kernel. But TMM bypassed the kernel. Kernel eBPF can attach to TMM — a uprobe on the tmm binary works today — but it can't afford to (every hit traps into the kernel, inside a run-to-completion loop) and it can't enforce (the kernel forbids overriding a return from a uprobe). So it can watch, expensively, and never act. Today, changing TMM's own code means the slow lane, every time:

change today C source → rebuild → re-qualify → release train weeks–quarters

◇ control plane

Linux daemons

httpd, MCPD and the other resident C daemons — ordinary processes the kernel can see. (Not tmsh: it is a shell that runs per command and exits, so an entry probe on it shields nothing. And iControl REST runs on the JVM while iControl LX runs on Node — three runtimes, so three adapter implementations.)

kernel eBPF reaches this ✓

◆ data plane

TMM microkernel

Own stack, poll loop — kernel-bypassed for speed. (Plugin processes like bd are ordinary Linux processes: reachable by a uprobe today.)

reachable only at a cost it can't pay ✗

Say it plainly: TMM is its own kernel. It plays every role Linux plays for the traffic it carries. Linux earned an eBPF VM inside it for exactly this job; a kernel of TMM's standing and maturity deserves its own eBPF hosting VM. That's the move.

And a proxy is the favorable shape for this. A packet-forwarding plane's unit of work is the packet, with a per-packet budget in single-digit nanoseconds — verified bytecode is a meaningful fraction of that, which is why it struggles to earn its place there. TMM's unit of work is a flow, a connection, a request: terminate TCP, negotiate TLS, parse L7, evaluate policy — microseconds where a forwarder spends nanoseconds. A hook costing tens of nanoseconds is noise against that, and the hooks worth having sit at warm per-request boundaries, not in a per-packet fast path. A proxy also has state worth looking at — listeners, profiles, parser state, plugin internals — which is exactly where its CVEs live.

02 the move

Give TMM — a microkernel — its own eBPF.

F5 has a long history of extending programmability into the runtime data plane — this is its next step.

It's entirely buildable, because what makes kernel eBPF safe was never the kernel: it's a static verifier and a small sandboxed VM. The verifier analyzes the bytecode and proves — before it ever runs — that the program is bounded (every path terminates in a known number of steps; it cannot loop forever) and memory-safe (every load and store stays inside the bytes it was handed; it cannot read what it wasn't given or scribble on TMM's memory). Both are libraries. Neither needs the kernel. Termination isn't the whole of hot-path safety — a per-hook time budget handles the rest (§5.4); the verifier is the floor, not the ceiling.

So bring them inside. Embed a small userspace eBPF VM — uBPF, ~150 KB, JIT-compiled — inside TMM's own address space, at designed-in hook points, gated by a stock verifier (PREVAIL). Now behavior arrives as bytecode, proven safe before it loads. No rebuild. No reboot. The data plane gets a fast lane:

change todayC source → rebuild → re-qualify → release trainweeks–quarters
the proposalauthor → clang → PREVAIL verify → budget pass → sign → loadhours

And the mechanism isn't hypothetical. Microsoft's eBPF-for-Windows ships this pair — uBPF as the execution engine, PREVAIL as the verifier — in a maintained, production-used component. The verifier half is the well-trodden part; the JIT is where we do our own hardening (§5.4). A userspace VM running verified bytecode at a designed-in hook is an established pattern with a maintained implementation behind it; what's new here is bringing it to a proxy data plane that hasn't had it. The parts we'd build are the parts that are ours anyway: the hooks, the host-owned outcomes, and the signing gate.

And the hooks map onto structures TMM already has — and new ones it will define — so the surface can start from what's in the code today and grow as the code does, not a blank page. A candidate catalog of USDT tracepoints (userland statically-defined tracing — named probe points designed into the source) can be drawn up alongside the engine, right where that state already lives: L3/L4 ingress and the connection table, the TLS record layer, the L7 parsers, the plugin processes, the poll loop itself. Each hook that lands adds one more place to observe, one more place to act.

runtime· programmable· provably safe

Three properties, equal weight — and nothing else brings all three in-process, at the data plane:

iRules runtime, but not provably safe
DynaD runtime too — an earlier scripting-based swing at exactly this, since deprecated. What's different now: an unverified script had no proof, no signing gate, and no host-owned outcome set — the three things that make this one governable
WASM programmable, but its guarantees are enforced dynamically — bounds-checked as it runs, time bounded by a counter that aborts. eBPF moves the same guarantees earlier: memory safety and termination proven before load. Both still need a runtime time guard; ours is §5.4
kernel eBPF provably safe, but in the wrong kernel — a USDT lets it watch TMM, not act inside it, and traps on every hit

An embedded eBPF engine is the only surface that is all three, in-process — reaching the data plane's own code and state.

Complementary, not a replacement. iRules stays the first line for traffic logic, WASM the home for rich extensions. This reaches the layer none of them can, and modernizes that lineage for the AI age.

03 one shape · observe · act

Observe and act are the same machinery. Only the last step differs.

First, what a program is. It isn't a process that runs on its own — it's a small event handler, a callback the engine invokes at a hook, triggered by the very thing it's watching: execution reaches that point in the code, the program fires, and it's handed a curated context describing what's there. In its simplest shape it reads that context and returns a value — the engine can do far more, but this base shape is all the symmetry needs. Whether the host records that value as a metric, uses it to stream a window of live internal state out to userspace — for discovery, root-cause analysis, debugging, and uses still to come — or treats it as a decision to act on is its choice, not a different mechanism.

So how would you write one? You write a few lines of C and compile with clang -target bpf — or, for one-line probes, tmmtrace, a proposed authoring front-end that emits the same bytecode: bpftrace for TMM. You describe the probe in a small, familiar language and it does the rest — compile to eBPF bytecode, verify, and, once signed, attach at the named hook. One line or a full multi-probe script, same path.

And it spans both planes from one grammar: point a probe at a data-plane hook and it runs in TMM's embedded VM; point it at a control-plane daemon and it rides kernel eBPF — one language for the whole box. Each probe is three parts:

tmm:<stage>:<event> /predicate/ { action } which hook · tmm: / ctl: when it fires what to do

The action is the only part that decides observe vs. act. Same hook, same predicate — flip the verb:

Same program shape; the host records the return. This is observability — deep telemetry from inside a black box, on demand, then off. Same program shape; the host acts on the return. This is control — here, steering the flow the program flagged toward a healthier pool member.

Nothing about the VM, the verifier, or the context changed — only what the host does with the answer. That symmetry is the thesis: one verified surface, serving observation and control as equals.

And read-a-context, return-a-value is just the floor. The hook surface is designed to grow — a widening catalog of designed-in USDTs, plus every named function the build's signed hook map already exposes, each new context field opening more of the data plane to both observation and control, with room to give programs more power over time.

04 what the engine unlocks

A general-purpose programmability platform for the data plane.

One engine — a verified program running at a hook — covers a wide span of everyday programmability and observability inside a black box:

  • Deep observability. Counters, latency histograms, and a flight recorder from inside a kernel-bypassed data plane — summarized with tmmtrace (bpftrace for TMM) or captured byte-for-byte with tmmdump (tcpdump for TMM).
  • New logic, telemetry & tuning. Behavior and metrics shipped as bytecode, no TMOS rev — a metric you didn't think to collect, or reading internal load to nudge a knob.
  • In-path control. Steer, sample, rate-limit, or gate a flow on an internal signal — the decision computed right at the hook, inline, with no round-trip out of the data path.
  • Field diagnostics. Ship a signed probe to characterize a production issue in situ, then pull it — no debug build, no core-dump archaeology.
  • Runtime CVE mitigation. Recognize a bug's precondition and take a host-owned safe outcome, between patch windows — the one application worked end-to-end, with its limits, in the CVE walkthrough. It is one use of the engine, and the narrowest: it needs the same hooks, the same verifier and the same signing gate as everything above it.
  • AI-authored programs. Because safety is a proof, not trust, a model can draft one and the verifier is a fail-closed acceptance gate — blast radius bounded before a human signs.

Every one of these is the same engine. A verified program runs at a hook; they differ only in what the host does with its result. A new capability ships as verified bytecode, on demand, then retires — not as a TMOS release.

05 under the hood · for the engineers

How the engine works.

Everything above rests on one small, in-process call, gated by a static proof. Here's the machinery — the call, where it sits, why it's safe to run inline, and how the surface grows.

5.1 The engine & its hook points

What's embedded in TMM is a full in-process eBPF engine — a JIT-compiled VM that runs arbitrary verified bytecode — not a single-purpose gate. A hook point is a named spot in TMM's own source, placed by F5's engineers, where that engine runs a program over a curated view of the code's local state. The same machinery feeds counters, latency histograms, and flight-recorder rings for deep observability, streams captured windows of internal state out to userspace for RCA, and drives steering and self-tuning where the host wants to act on the return. Returning a value the host acts on is one thing the engine does — not the point of it.

Two kinds of hook — the anticipated and the unanticipated. The first is a designed-in tracepoint (a USDT): F5 places a named, versioned point exposing a curated ctx — a stable contract, published in a per-build map. That is the planned surface, and it is where the standing value lives: the metrics, histograms and latency breakdowns you want on every box, whose meaning holds across releases. But no catalog anticipates every question. F5 cannot pre-place a tracepoint for every question someone will need to ask three years from now — which is what the second kind is for.

The second is a function-boundary probe: attach the verified VM at the entry or return of an existing named function — any function that survived the build as its own out-of-line body — reading that function's arguments and reachable state as the ctx. It rides the code's existing structure — functions and their signatures — so you can instrument a spot nobody thought to instrument ahead of time, with no new build. That is what makes the engine answer questions it was never designed for: why is this one customer's TLS renegotiation path slow, what state does the parser hold when this rare error branch fires, which flows are reaching a code path we thought was unreachable — and, as one case among those, recognising the precondition of a bug nobody foresaw. (The mechanism is the kernel's own fentry/ftrace trampoline model, applied to TMM's own functions.)

Both stay designed-in, not injected. F5 owns the source and the symbol table, compiles the hook capability in (patchable function entries), and attaches at a named symbol — never fragile offsets an external tool guesses at in a foreign process. A hook with nothing attached is dark until lit. And the honest bound on reach: which functions are hookable is decided by the optimiser, not by us. At -O2 an inlined or identical-code-folded function has no entry pad of its own, and a cloned one (.constprop, .isra) changes both its symbol name and its argument list. So the hookable set is whatever the build's signed hook map says it is — which is knowable per build, but is a subset of the source, and pinning a specific function into it means marking it noinline: a source change, with its own cost.

The honest trade is stability: a tracepoint's ctx is a curated, versioned contract; a function-boundary probe's is build-specific (function X's signature at build Y) — more reach, a looser contract, re-validated per build. Either way it is verified, signed, and budgeted before it runs.

// at a hook point in TMM: pack a curated snapshot, run the VM struct l7_ctx ctx = { .opcode = f->opcode, .len = f->len }; ubpf_exec(vm, &ctx, sizeof ctx, &ret); // ret is the program's result; the host decides what it means: // summarize → recorded as a counter, histogram, or ring // capture → a window of state streamed out to userspace (RCA, debug) // act → a decision from the host's set — e.g. steer / drop

The ctx is the program's entire world — it's input; what the return means is the host's choice — a value to record, a window to capture and stream out, or a code to act on. In the base tier, programs are pure functions of ctx — they read fields and return a number, and call nothing; the host owns the counters, histograms, rings, and any decision logic around the call. Two consequences fall out, and they erase the hardest parts: no custom helpers to define, register, or secure; and stock PREVAIL — a bounded predicate over a typed context is the canonical case the verifier already proves, so there is no fork in the trust path.

5.2 Placement — two planes, two engines, one catalog

A single mechanism can't cover TMOS, because TMOS is two execution environments. The plane decides the engine.

PlaneWhat runs thereEngine
ControlLinux daemons — httpd, MCPD; iControl REST on the JVM; iControl LX on Node kernel eBPF / uprobe · + JVMTI · + V8
DataTMM microkernel — kernel-bypassed (plugin processes are ordinary Linux processes) embedded uBPF (+ PREVAIL)

The control plane reuses the kernel's own verifier; the data plane is the crown jewel, where an in-process VM is the only thing that can reach inside TMM's own execution affordably, and act on what it finds. Either way, one front-end drives both: you author with tmmtrace against a hook by name, and its namespace picks the engine — a ctl: hook compiles to kernel eBPF (kernel verifier), a tmm: hook to embedded uBPF (PREVAIL). One DSL, two engines, one trust path. (Not one binary for both: a different engine means a different ctx and a different verifier, so retargeting is a re-author, not a rename.)

5.3 Three form factors — same mechanism, honest coverage

Appliance, VE, and BIG-IP Next all run the same TMM, so the mechanism is identical. Coverage is not — it scales inversely with how much the platform offloads to hardware.

Form factorData pathCoverage
BIG-IP VEpure software, no offloadfull — the VM sees the entire path
Appliancehardware offload (ePVA, FPGA/TurboFlex)software path only — offloaded flows are a hardware boundary
BIG-IP Next (BNK)containerized TMM, DPU-dependentdepends on how much the DPU steers vs. lands in TMM

Honest boundary: a flow handled entirely in silicon never enters TMM software, so an in-TMM hook can't see it — the same limit iRules and kernel eBPF already have. The L7/parser stages and the plugin processes worth reaching execute in software regardless, so they stay in view.

5.4 Why it's safe to run inline

Start with the load-bearing assumption, named plainly: every claim on this page leans on the verifier being right. Three reasons that's a strong bet. Provenance — PREVAIL is the verifier Microsoft ships in eBPF-for-Windows: built on abstract interpretation, a formal method rather than hand-grown heuristics, publicly maintained and hardened in production. Narrow envelope — this design uses it at its best-proven case: a bounded predicate over a small typed struct, no helpers, no maps. Depth — and this is the load-bearing point. The JIT emits native code inside TMM, and the verifier gates what reaches it — PREVAIL itself runs off-box at build/control-plane time — so an unsound verifier would still mean arbitrary code in the data plane — the risk a security review will press hardest. But only bytecode F5 authored ever reaches the verifier — it runs in F5's admission pipeline, before signing — and only F5-signed bytecode ever reaches the in-TMM JIT; attacker-controlled input never touches them, so a soundness bug is not a traffic-borne RCE — it's a supply-chain concern, gated by signing-key protection. A per-hook watchdog stands behind all of it. Trust the proof; don't depend on it alone. (The load-bearing problems are catalogued in the engineering register.)

The second principle is just as blunt: verified ≠ secure, and verified ≠ correct. PREVAIL proves a program is memory-safe and terminates — not that it fits the hook's budget, and nothing about intent. Time-safety and security both live in the governance around the VM:

  • Proven before load — bounded memory + termination, or it's rejected (fail closed).
  • Bounded in time, not just in steps — a proof that a program terminates is not a worst-case execution time (WCET): the longest it can actually take on the hardware. So each hook adds an instruction-budget ceiling at load and a runtime guard as it runs — a provably-terminating program still can't overrun its hook's budget — the guard's mechanism is the register's §01 open question — which is set per invocation and gated by the hook's rate (per packet, per connection, per request), not by one global number.
  • Signed & authorized — the box checks the signature before the JIT sees bytecode (the verifier already ran, at F5); a program that acts needs stricter authz than one that only observes; RBAC-gated.
  • Host-owned outcomes — a program only returns a value; everything done with it, the host does. Even at an acting hook, the return merely selects among outcomes the host code already owns (steer / drop / sample, from the canonical set); a program cannot invent control flow or force an arbitrary early return.
  • Context minimization — the signed hook-point map declares, per hook, exactly which ctx fields are exposed; secrets and PII are withheld by default.
  • One-way egress — with no helpers a program has no I/O of its own; it returns a value to a host-owned, schema-checked sink it cannot read back or redirect. The verifier proves the program reads only its declared ctx fields and has no exit of its own; the host owns the single sink — so only host-approved derived output ever leaves, never raw memory.
  • Governed lifecycle — attestation/inventory, tamper-evident audit, instant kill-switch + revocation, a per-hook perf budget with a watchdog, and a control-plane canary that auto-unloads on a health signal — because a verified, signed program can still be wrong (black-hole or misroute traffic); the proof bounds crashes, the canary bounds bad-but-valid programs.

5.5 Lifecycle — nothing outlives its purpose

Every program is authored, proven, signed, loaded — and can carry an expiry, so nothing outlives its purpose: a diagnostic probe when its window closes, a temporary control when it's no longer needed. No zombies.

author (human or AI-assisted)→ clang → bytecode→ PREVAIL verify→ budget pass→ sign→ load → run→ auto-retire

5.6 The surface is built to grow

Read-a-context, return-a-value is the floor — chosen for maximal safety, not the limit of the VM. Two growth paths, deliberately different in cost:

  • More hooks, cheaply. Each release can add USDTs (define a ctx, place a hook, publish it in the signed map — each rides a build), and function-boundary hooks come with the compiler flag — no VM, verifier, or helper work either way. Honest cost: the flag pads every function entry in the image, so there is a one-time build-time footprint (i-cache/size) paid whether or not a hook is ever armed — a number to measure before committing, not to assume. Every new field widens what can be observed and acted on, so the instrumentation surface compounds over time.
  • Helpers — if and when needed. Richer, stateful programs (direct host-map access, cross-flow state) can be enabled later through an optional helper tier. The honest trade: helpers reintroduce an ABI to secure and verifier surface to manage — which is exactly why the base ships without them and stays on stock PREVAIL. Power is available; safety stays the default.
