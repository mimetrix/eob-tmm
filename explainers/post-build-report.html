EOB · TMM — build report · 2026-08

Every piece is built, run, and measured on real hardware.

The proposal: embed a small userspace eBPF virtual machine — a sandbox that runs tiny verified programs — inside the TMM data plane, and use it to shield a function nobody edited when a CVE lands, with no rebuild and no restart.

This page is the state after building it. The mechanism is proven end to end on a bench. What is not yet done is the same thing inside a shipping TMM under live traffic.

01 the honest boundary

"Built" means run on a bench — not shipped inside TMM.

Every result here comes from small standalone programs that compile and run on a dev machine — the same instruction set TMM ships on — exercising the real mechanism against a real function. They are evidence, not a product.

That line matters, because the two claims are worth very different amounts. "The code patch executes and the verdict controls the function" is proven. "This runs inside a live TMM, arming an untouched function while traffic flows, and stops a real CVE arriving over the wire" is not — it is the remaining work, mapped and named, not hand-waved.

02 the reveal

The VM's verdict decides whether the hooked function runs.

When an armed function is entered, control jumps to a tiny hand-written stub — the trampoline — which hands the arguments to the VM and runs the shield program. The program returns one of two answers, and that answer steers the function's own body.

one armed function, two shield verdicts
enter victim() → trampoline → VM → run the body → 0xBEEF

FALLTHROUGH. The shield says the input is fine, so the trampoline returns into the real body. The caller sees the body's normal result — exactly as if nothing were armed. SAFE_RETURN. The shield says the input is dangerous, so the trampoline skips the body entirely and hands the caller a declared safe value. The crash never happens.

This is not a stub deciding — it is a real, verifier-checked program running in the VM, on a real armed function, choosing the path on every call.

03 the thesis

Four hard seams — each proven, now running as one flow.

the mechanism, in four moves

patch· decide· swap· join

Each was the kind of thing a review would stop on. Each was built and run until it held:

patch own codea process rewrites its own running code so the CPU executes the change — via the same path a debugger uses
decidethe trampoline + VM run a verified program and its verdict steers the function's body
safe swaparm and disarm while other cores run that exact code, with no torn or stale instruction ever executed
joinall three at once — the swap arms the real trampoline, and the VM decides, under multi-core load

Separately proven before. Now one flow — and it stays clean under billions of calls.

Reused, not reinvented: the VM is uBPF and the verifier is PREVAIL — both upstream open source, on their current versions. What F5 builds is the embedding: the trampoline, the arming, the safe swap, and the host glue.

One honest wrinkle. Across two 20-minute safe-swap soaks of the real code path, one run produced a single, non-recurring, recoverable fault — never a corrupt return. The suspect is the kernel's write into executable code briefly disturbing a core reading the same page. Correctness (no torn or garbage instruction) held across ~12.5 billion calls; the rare transient is recorded for the threat-model review, not papered over.

4.4 The end-to-end demo — the target, not yet run

The bench proves each seam and the join. The deliverable is this sequence inside a live TMM, driven by real traffic. It is the goal the remaining work aims at, shown here so the gap is explicit.

drive the CVE → crash→ arm the verified shield (no rebuild)→ drive again → no crash→ disarm→ crash returns

On the bench today, the shield's decision is proven on a synthesized input and trivial driver programs. Reaching the real null-dereference over the wire is part of the last mile.

05 the last mile

The mechanism holds. What remains is putting it inside a live TMM.

The hard, novel parts — patching running code, deciding with a verified program, swapping it in safely while cores run it — are built and measured. The remaining work is integration and proof-in-place, not invention:

  • Move the swap into TMM's own per-core threads, and choose between the breakpoint dance and a quiescence point in the poll loop with the real loop in hand.
  • Make the safe-swap fault handler coexist with TMM's crash agent, scoped to only the patch bytes.
  • Confirm two TMM-specifics: whether its code pages are huge pages (proven on normal pages), and the production node's code-integrity policy.
  • Trigger the real CVE over the wire and run the crash → arm → no-crash → disarm demo end to end.
