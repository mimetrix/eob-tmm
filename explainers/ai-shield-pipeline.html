A design proposal · AI-authored data-plane shields

AI collapsed disclosure-to-exploit. So must disclosure-to-mitigation.

A pipeline that reads a CVE — advisory, proof-of-concept, patch diff — and produces a machine-verified, signed, auto-retiring data-plane shield: bytecode that blocks the exploit path inside F5 TMM, in hours, without a rebuild. The twist that makes AI authorship safe here: a static verifier proves the output can't crash the box, so blast radius is bounded by proof — not by trust in the model.

Where this stands: a proposal built on the embedded-eBPF substrate. The verifier and exploit-replay gates already run in a working prototype; the CVE-to-predicate front stage is the piece this lays out.

CVE → predicate → bytecode verifier-as-oracle closed-loop, self-correcting human on the trigger

The premise

The window closed on the defender

Machine-assisted vulnerability discovery reasons over huge, mature codebases at machine speed. The interval from a CVE becoming known to it being exploited has compressed toward zero — but a data plane still can't take an emergency maintenance window on demand.

Attacker, today

AI-speed offense

Finds and weaponizes obscure conditions in hours.

No safety obligation. No review board. No proof required.

Defender, today

Human-speed mitigation

An expert reads the advisory, hand-writes a probe, validates it — then waits for a change window.

Scarce, slow, and it doesn't scale to the volume of modern disclosure.

The move

Give the defender a symmetric lever: AI that authors the mitigation. But defensive AI carries an obligation offensive AI never does — the output runs inline in the data plane, where a bad program crashes the box. So the whole design turns on one question: how do you let a model write code for the hot path without trusting the model?

The key idea

You don't have to trust the model

You could never let a model write a kernel patch and ship it inline — unbounded output, no way to prove it's safe. An eBPF shield is different in kind. It lives in a class of programs whose worst case is provably harmless: a static verifier proves it terminates and touches only memory it's allowed to, and the host owns the outcomes — the program can only pick PASS or DROP, never invent control flow.

So confine generation to that class and something powerful happens: the identity of the author stops mattering to blast radius. Human, toolchain, or language model — if the verifier accepts it, it cannot crash or hang the data plane. An unbounded trust problem becomes a bounded proof problem.

Two design decisions make it work, and they're the inventive core:

Decision 1

The model emits a constrained expression, not code

Not raw bytecode, not C — a bounded predicate one-liner whose only vocabulary is the typed fields of a chosen hook in a signed, per-build hook-point map. The representation itself is the guardrail: the model literally can't express an unbounded loop or a wild pointer.

Decision 2

The verifier is a mandatory, automatic gate

Every candidate passes a static verifier before it can load, fail-closed. A candidate that doesn't verify is discarded automatically. Safety is proven, not reviewed — which is exactly what lets a machine be the author.

The model picks from a menu it didn't write

Both decisions rest on one fact: the hook-point map is TMM's, not the model's. Those hooks and the typed ctx each one exposes are designed into TMM ahead of time — signed, emitted per build — before any pipeline runs. The model doesn't invent a hook or a field; it selects a hook and writes a predicate over the fields that hook already exposes. So the pre-existing catalog is itself a guardrail alongside the verifier: the AI's entire vocabulary is what TMM already chose to expose, and it can't reach for instrumentation that doesn't exist. It's a consumer of TMM's instrumentation contract, never its author — which is also why "is this CVE even addressable?" is answered by that map (the shieldability step below), not by the model.

The pipeline

CVE in, verified shield out — a loop that closes itself

Every early stage has a mechanical oracle, so the loop can run to green before a human ever looks. The human reviews only candidates that are already proven safe, proven to block the exploit, and proven to spare legitimate traffic.

1

Comprehend the artifact

Read the advisory / PoC / patch diff; derive the discriminating predicate — what separates the exploit input from legitimate input. (The classic SIRT-analyst task.)

2

Emit a constrained one-liner

Grounded on the signed hook-point map + types — a predicate over typed fields at a real hook, not free-form code.

tmm:l7:frame /args.opcode >= 4/ { drop(); }
3

Compile to sandboxed bytecode

Deterministic, downstream of the model. The bytecode is the artifact the oracles judge.

✓

Three mechanical oracles

The candidate must clear all three — automatically. Any failure feeds the refine loop.

Oracle 1

Verifies

Static verifier proves bounded + memory-safe.

fail → discard
Oracle 2

Blocks the PoC

Replay the known exploit — is the vulnerable outcome prevented?

pass → effective
Oracle 3

Spares legit traffic

Action rate vs. a benign corpus below threshold.

pass → low FP
⚑

Human authorizes + signs

The model proposes; a human authorizes. The signing key is never autonomous — AI in the loop, human on the trigger.

↺

Deploy observe-first · time-boxed · auto-retire

Ship telemetry-only first where possible; time-box it; auto-disable the moment the patched build is detected. Every blocked attempt captures its run-up, which refines the next predicate.

↻ any oracle fails → refine & regenerate (bounded retries) → or declare NON-MITIGABLE

Knowing when to say no

“Not shieldable” is a first-class answer

A synthesis system that always returns something is dangerous. The pipeline includes a shieldability classifier that decides, from the CVE and the hook-point map, whether a safe interception point even exists — and when it doesn't, says so.

Needs all three

What makes a CVE shieldable

A hook that runs before the vulnerable operation, exposes the discriminating condition in its typed args, and offers a clean outcome that leaves the process consistent.

Honest failure

When one is missing

Crash-before-the-first-hook, hardware-offloaded fast path, or no clean abort branch → the classifier emits NON-MITIGABLE → engineering hotfix, instead of shipping an unsafe half-measure.

The honest limits

Where AI does not get the keys

Verified ≠ correct

The verifier proves safe, not right

A predicate too broad drops legitimate traffic (self-inflicted DoS); too narrow is bypassable. That's caught by the false-positive corpus and human red-team — not the verifier. Those stay mandatory.

Human on the trigger

Signing is never autonomous

No agent pushes to the fleet. The model drafts and self-tests; a human authorizes. Ground truth is the PoC replay, not the advisory's prose — which could be wrong or poisoned.

Residual dead zone

Some CVEs aren't runtime-shieldable

And some data-plane traffic is offloaded to hardware, invisible to any software shield. The classifier names these honestly rather than pretending to cover them.

The one thing to keep straight

The verifier is a safety gate, not a correctness gate and not a security gate. It's what makes machine authorship safe to attempt. Making it correct and trustworthy is the job of the replay oracle, the false-positive corpus, mandatory signing, and human red-team — the governance around the loop.

Where this stands

Two of the three oracles already run

A working prototype — tmmtrace over the minimm stand-in data plane — already compiles a bounded one-liner to an eBPF shield, gates it on the real PREVAIL verifier (Oracle 1, fail-closed), and replays the exploit to confirm it blocks while the data plane survives (Oracle 2). The generative front stage is a drop-in over the same DSL target and the same oracles it would iterate against.
